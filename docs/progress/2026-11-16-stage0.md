統括（毎日の回しのセッション）から頼まれた作業。運営者の 11-16「早く利用者が使える状態に」。作業の枝は `intake-feedback`。提出の版（タグ submission・枝 hackathon-release）には触れていない。

## したこと

### 1. 台帳の受け口をアプリにつないだ
- `src/bridge/ledger-intake.ts` の `LEDGER_INTAKE_URL` に、運営者が配置した本物の受け口（`https://moyai-ledger-intake.white-violet-b87a.workers.dev`）を入れた。
- 試験が本物に送らないように、`MOYAI_LEDGER_INTAKE_URL=off` で道を出さないようにし、vitest の設定・Playwright の 2 つの設定・e2e の橋渡しの既定に付けた（受け口を使う試験は試験の台の道で上書き）。URL を入れると、どの試験からも本物に届く形だったので先に塞いだ。
- SHARE の「MOYAI 経由」が出て、主ボタン 1 つで送れることは、今ある e2e（`tests/e2e/ledger-intake.spec.ts`、偽の受け口）がそのまま通る。
- 通信の例外の文：`src/shared/security.ts`（→ `docs/security.md` を `MOYAI_WRITE_DOCS=1` で作り直した）・`docs/plan.md` §2.12 を実態（台帳は moyai-ledger、受け口は配置済み、フィードバックも同じ受け口）に合わせた。

### 2. 読み方のフィードバックを受け口から Issue に
- 受け口に `POST /feedback`（`services/ledger-intake/src/feedback.ts`）。形（`parseReadingFeedback`・キーの重複・深さ）→ 業種 → 行の値らしきもの（`countValues`）→ 同じ中身の Issue → 開いた Issue 20 まで → Issue を出す。件数・IP の数え方・転送をたどらないのは `/submit` と同じ（数える名前だけ別）。行き先は `FEEDBACK_REPO`（`wrangler.jsonc` の vars、`mushitaro/moyai`）。
- 毎日の回しと同じ字で数えるため、行の値の数え（`scripts/skill-loop/values.mjs`）と Issue の型の見出し（`scripts/skill-loop/form.mjs`）を `feedback.mjs` から外に出して、両方が使う形にした。
- 見つけて直したこと：`feedback.mjs` はルールの欄の JSON をそのまま数えるので、アプリの書き出しの `cells`（効いたセルの数）が 1,000 以上だと「4 桁以上の数」と数えて返していた（アプリから貼った正しいフィードバックが返される）。書き出しの形のときだけ `cells` を 0 に置き換えてから数えるようにした（`countableRuleBlock`。ほかの 4 桁の数は今のとおり数える試験を足した）。
- 固有名詞の網：その PC の語（網 2）は語そのものが固有名詞なので受け口に送らない。アプリの送る経路が送る前に照らす。受け口は会社・施設の名前の形（`countValues`）で照らす。
- トークン：fine-grained のトークンの権限は選んだリポジトリのどれにも同じに付くので、台帳のトークンに moyai を足すと moyai の Contents にも書けてしまう。だから足さずに、moyai だけ・Issues だけの別のトークン（秘密 `FEEDBACK_TOKEN`）にした。手順は `docs/ledger-deploy.md` §2.1。無ければ `GITHUB_TOKEN` を使い、権限が無いので 503 `intake.feedbackNoPermission` で返す。
- アプリ：人だけの経路 `reading_feedback_send`（`HUMAN_ACTIONS`・`ROUTES`・橋渡しの経路の表）。保管先の feedback/ に保存したのと同じ全文だけを送る。ルールのシートの主ボタンは 1 つのまま：書き出す → 保存する → 送る →「✓ 送信　Issue #n」（押せなくなり「理由：送信済み」）。送る前の結果の 1 行は「公開の Issue になる。送ったあとは消せない。」。受け口の無い版では「送る」を出さない。
- 先に絵：Wire Frame に「ReadingOutSend」を足した（今の ReadingOut はそのまま並べて残した）。

## 見直し（別の役が差分だけを読んだ）
- 重いものは無し。人だけの経路・転送・トークンと IP の出し方は合っている、との読み。
- 直した：① ラベルが付かなかった Issue が残り、送り直すたびに増える → 閉じる。② 同じ中身の探しと開いた数の上限が、閉じた Issue も含めて 500 件で止まる → 開いた Issue だけを読み、受け口が本文に書く印（ルールの欄の SHA-256）で数える（手で立てた Issue を返さない・数えない）。③ 行の値らしきものが受け口で初めて止まる（PC の外に出たあと）→ アプリの送る経路でも同じ数え方で先に止める。④ 試験の止め（`MOYAI_LEDGER_INTAKE_URL`）が "off" ちょうどでないと本物に落ちる → 環境変数があれば、手元の試験の台の道のほかは道を出さない。橋渡しに env を渡す試験でも、プロセスの env の止めを効かせる。⑤ 受け口の断りの言葉を分けた（業種・たまり・ラベル）。⑥ `FEEDBACK_TOKEN` が空なら `GITHUB_TOKEN` を使う。
- 直さなかった：網 2 の語は画面が渡す（橋渡しが計画から作り直していない。保存の経路と同じ。タブの秘密と 1 回きりの印を持つ呼び出しだけが渡せる）。確かめの印 `[X]` は、人が全文を見て「送る」を押したことの代わりにしている（文を足すかは運営者の判断）。
