`docs/plan.md` §2.8 の F2 共有のうち、帯の境目（決めた値と理由と測った数）、紛れる数 k の段の順、公開の台帳（場 2）の検証・PR の照らし方・集計・サイト・架空の束の作り方を書く。数はどれも試験の実行か、この PC で道具を走らせた結果で、手で書いた数は無い。

## 1. 帯の境目（2026-11-03 に決めた。版 `bands-2`）

帯は束の型と台帳の検証の版に入る（束の body の `bands`）。境目はコードの定数 `src/share/bands.ts` の 1 か所だけにある。場の決まり（`circle.json`・`ledger.json`）は、内側の境目を外す（粗くする）向きにだけ変えられる。帯は下の端を含み、上の端を含まない。

### 1.1 間隔（interval）

| | fictional-1 | fictional-2 |
|---|---|---|
| 台帳に出る塊 | 12 | 13 |
| 帯にする前の中央の間隔（年） | 1・2・3・6 | 1・2・3・6 |
| 帯 | I1 5・I2 2・I3 3・I6_7 1 | I1 6・I2 1・I3 4・I6_7 1 |

- 細かさ：毎年（1）・隔年（2）・3 年に 1 回（3）が別の帯になる。精密機能検査の「三年に一回以上」と比べるには、1〜5 年を 1 年ずつに分けておく必要がある。I6_7 は、工場が入れた精密機能検査の抜け（6 年あいた）がそのまま見える。
- 粗さ：間隔の列は全国の表に無い。間隔だけで施設を絞る道は、全国の表からは無い（全国の表に無い知識との突き合わせは防げない。§2.8 の保証できないこと ③）。
- 6 年からは幅を広げる（6〜7・8〜10・11〜15・16〜30）。長い周期は記録の年数が足りず、1 年の差に意味が薄い。

### 1.4 経過年（ageAtWork）— どこにも出さない

帯の幅の問題ではなく、組み合わせの問題だと測った。

1. 塊には作業をした年度（`years`）が出る。最初の年度と経過年の帯がそろうと、受け手は「設置の年度 ∈ [最初の年度 − 帯の上, 最初の年度 − 帯の下]」と読める。
2. 塊ごとに最初の年度がずれると、幅の重なりでさらに絞れる。工場の正解の世界の輪向けの束に経過年があったとして（`bands-1` の写し取りと同じ作り方）重なりを取ると：
   - fictional-1：設置の年度は 2001〜2004 の 4 年（正解は 2001〜2002 年度）
   - fictional-2：1997〜1999 の 3 年（正解は 1997〜1998 年度）
3. 全国の表には使用開始年度の列がある（施設名と並んで公開されている）。見え方（段の順で k ≥ 5 に届いた段）の中で、使用開始の年をその幅に絞ると、5 施設に届かない施設の数（844 のうち）：

| 年の幅 | k < 5 の施設 | k の中央 |
|---|---|---|
| ちょうどの年 | 696 | 2 |
| ±1 年（3 年） | 479 | 4 |
| ±2 年（5 年） | 356 | 6 |
| 西暦の 5 年の区切り | 361 | 6 |
| 西暦の 10 年の区切り | 202 | 9 |

候補は、その施設が選んだ段で見え方の値が同じすべての施設（ほかの段を選んだ施設も入る。`kNational` と同じ数え方）。工場の束で読めた 3〜4 年の幅は ±1〜±2 年に当たり、479〜356 施設（57〜42%）が 5 未満に落ちる。帯を 10 年に広げても 202 施設（24%）が落ち、重なりで幅はさらに狭まる。だから境目を粗くするのでは足りない。

決めたこと：

- **経過年はどこにも出さない**（輪にも公開の台帳にも。2026-11-03 に運営者が決めた。下の 1.6 の道 B）。写し取り（`src/share/copyout.ts`）に経過年の作り手は無く、束の型（`src/share/bundle.ts`）・場の決まりの欄（`src/share/rules.ts`）・検問所の画面にも無い。設置の年は写さず、欄ごと写さなかった数（`installed`）に数える。
- 受け手は、輪でも台帳でも同じ数え直し（`recount`）で、塊に経過年の欄がある束を `shape.fieldRemoved`、経過年の欄を許す決まり（`circle.json`・`ledger.json`）を `shape.rules.fieldRemoved` で、理由つきで ✗ にする。欄の名前はコードの定数 `REMOVED_CHUNK_FIELDS`（`src/share/copyout.ts`）に置き、場の決まりで足し戻せない。前の版（`bands-1`）の束は `shape.bandsVersion` で ✗。
- それまでは公開の台帳にだけ出さなかった（定数 `LEDGER_WITHHELD_FIELDS` と理由 `ledger.fieldWithheld`）。輪にも当てたので、どちらも無くした。

## 3. 公開の台帳の検証（`verify ledger`）

台帳のリポジトリの形（`docs/plan.md` §2.8 場 2）：

```
ledger/ledger.json                                   台帳の決まり（管理者が署名。circle.json と同じ形で、厳しくする向きだけ）
ledger/TERMS.md                                      利用条件（検証では読まない）
ledger/bundles/<鍵ID>/<連番 6 桁>-<ハッシュ先頭16>.json
```

- 確かめるのは `src/share/ledger.ts` の `verifyLedgerFiles`。数え直しは輪の受け手と同じ `recount`、鎖は輪と同じ `checkChain`（`src/share/ring.ts`）。引数で緩める切り替えは持たない。
- 台帳 ID は ledger.json の body の変わらない部分（v・founder・nonce）から決まり、束の行き先（`to`）と照らす。決まりのハッシュ・全国の表と公開語彙のハッシュ・パックも照らす。
- 台帳だけの決まり（コードの定数。台帳の決まりで緩められない）：集団は `NATIONAL` だけ（`ledger.groupNotNational`）、`UPGRADE` の塊は ✗（`ledger.upgrade`）。
- 輪と台帳で同じ決まり（コードの定数）：経過年の欄がある束は ✗（`shape.fieldRemoved`）、前の帯の版の束は ✗（`shape.bandsVersion`）。経過年の欄を許す ledger.json は、決まりが ✗（`ledger.unreadable` と、コードの決まりで数え直した理由 `shape.rules.fieldRemoved`）で、どの束も数えない。CLI はパックを選ぶ前に止まり（終わりの値 2）、その理由を添える。
- 粒度（輪と台帳で同じ）：1 回だけの行（N1）に間隔があれば ✗（`grain.intervalOnN1`）、回数の帯が年度の数と合わなければ ✗（`grain.observedMismatch`）。
- 鍵 ID と出した人の結びつきは、束の署名をその鍵の公開鍵で確かめて決める（鍵 ID は公開鍵の SHA-256 の先頭で、フォルダの名前と照らす）。GitHub のログイン名は使わない。
- symlink（Windows の junction も）はたどらない。ledger/ の下の、決まり・利用条件・束の形の外のファイルは理由つきで ✗。ファイルは 1 MiB、JSON の入れ子は 8 段、ファイルの数は 20,000 まで。
- バイト列で受けた束の BOM も、黙って捨てずに形の外れ（`shape.bom`）に数える（この変更で輪の受け手も同じになった）。

CLI：`node dist/cli.js verify ledger <台帳のリポジトリの根>`（根の下の `ledger/` を指してもよい）。決まりと束ごとに ✓ か理由つきの ✗ を標準エラーに出す。終わりの値は、すべて ✓ なら 0、どれかが ✗ なら 1、引数が違う・台帳が無い・決まりかパックを読めないときは 2。

## 4. 台帳の PR の照らし（`ledger validate-pr`）

`pull_request_target` の検証のワークフローが呼ぶ。純粋な関数（`src/share/prdiff.ts` の `validatePr`）は、`git diff --raw -z --no-renames --no-abbrev <base>...<head>` の出力のバイト列と、base の木の ledger/ の項目と、追加の blob を読む関数だけを受ける。

- 許すのは、状態が追加（A）で mode が 100644 の `ledger/bundles/<鍵ID>/<連番>-<ハッシュ先頭16>.json` だけ。
- ✗ にするもの：削除・書き換え・改名・写し・型の変更（D・M・R・C・T）、symlink（120000）、submodule（160000）、実行の印（100755）、`.github/` に触れるもの（大文字小文字・全角も）、許す形の外の道、大文字小文字か NFC/NFD だけが base の道か PR のほかの道と違う道、ASCII の外・UTF-8 でない道、長すぎる・深すぎる道、1 MiB を越える blob、64 件を越える変更、256 KiB を越える diff の出力。
- 中身は、base の木に PR の束を足した台帳を `verifyLedgerFiles` で確かめる（形・署名・鎖・粒度・禁止語・数え直し・k）。JSON の `__proto__` のキーと知らないキーは ✗。鎖は base の束の続きでなければ ✗（連番の飛び・同じ連番の別の束）。
- 決まりとパックは base（既定のブランチ）の ledger.json から決める。PR は決まりを変えられない（ledger.json に触れる変更は ✗）。

ワークフローの呼び方（そのまま受ける）：

```
node ../moyai/dist/cli.js ledger validate-pr --base "$BASE_SHA" --head "$HEAD_SHA" --repo . --json ../out/result.json --markdown ../out/summary.md
```

- `--base`・`--head` は commit の SHA（40 か 64 桁の 16 進）だけを受ける（ブランチ名や `-` で始まる値は 2）。head を checkout せず、`git ls-tree -r -z`・`git cat-file -s`・`git cat-file blob` で読み、head の側のコードは走らせない。git はシェルを通さず引数の並びで呼び、外の diff・textconv を使わない。
- base と head が同じ commit（workflow_dispatch）なら「変更なし」として、その木の全部の束を確かめ直す。
- 三点の diff は共通の祖先が要る。checkout が浅い（fetch-depth: 1）と祖先が無いことがあり、そのときは 2 で止まる（ワークフローは `fetch-depth: 0` か、base の履歴も取ること）。
- `result.json`（`moyai.ledger-validate/0`）：`mode`（pr／all）・`ok`・`error` と `errorKind`（tool／input）・決まり（ID・ハッシュ・版・✓／✗）・ファイルごとの道（JSON の逃がし方で生のまま）・道の SHA-256・表示してよいか・✓／✗・理由のコードと日本語・数。
- `summary.md`：日本語の PR のコメントの本文。ファイル名はコードの枠に入れる。英数と `. _ - /` の外の文字を含む道（`@` の名指し・HTML・改行・`|` など）は名前を出さず、道の SHA-256 の頭で示す。
- 終わりの値：すべて ✓ なら 0、どれかが ✗（PR の側の数・大きさ・空を含む）なら 1、引数・git・決まり・パック・diff の形の誤りは 2。

## 5. 受け手とサイトの集計

`src/share/aggregate.ts`（純粋な関数）。入力は確かめて ✓ になった束（鍵ごとに最新の 1 つ）だけ。

- 似た施設：受け手の見え方の軸ごとに、相手の値の細かいコードが受け手の値の範囲に入り、集団が同じ束。自分の鍵は数えない（サイトには自分が無い）。集団を混ぜない。
- 統計の行：塊（分類 × 作業の属性）ごと、間隔・工数・日数のそれぞれで、n（その欄のある、自分を除いた施設の数）が 0〜2 なら x、3〜4 なら幅の帯と n、5 以上なら中央の帯・四分位の帯・n。帯は順の値なので、中央と四分位は最近順位法（並べて ⌈p·n⌉ 番目）で取り、いつも実際にある帯を出す。場の決まりで粗くした帯の順でも数える。
- 匿名の札：鍵の指紋の頭 4 文字（「類似施設 7KQ2」）。頭がぶつかったときだけ 2 組・3 組と延ばす。鍵だけから決まるので、束やほかの施設が増えても変わらない。
- 似た施設が 5 に届かなければ「この条件では 5 施設に届きません」を出す。

## 6. 公開の台帳のサイト（`ledger site`）

Pages のワークフローの呼び方（そのまま受ける）：

```
node moyai/dist/cli.js ledger site ledger _site
```

- 1 つ目の引数は台帳のリポジトリの根（その下に ledger/ledger.json と ledger/bundles/）。出すフォルダは無ければ作る。
- `verify ledger` と同じ関数で確かめ直し、✓ の束から集計した 1 枚の `index.html` だけを書く。生のファイル（束・決まり・利用条件）は写さない。✗ の束は集計に入れず、数と理由を出す。
- 描くもの：【架空】の帯、台帳の決まり（ID・版・月・ledger.json の SHA-256・管理者の鍵の指紋・下限・欄・帯の境目・パック・公開語彙と全国の表のハッシュ・台帳に出さない欄）、✓／✗ の数、見え方ごとの節（似た施設の多い順）に、匿名の札ごとの年度の印と帯、塊ごとの統計の行。
- 文字はすべてエスケープする。CSP は `default-src 'none'` で、中の `<style>` 1 つだけをその SHA-256 で許す（スクリプト・画像・書体のファイル・接続・フォームは無し）。外への要求は無い（Playwright で Chrome と Edge から確かめた）。書体は端末の BIZ UDPゴシック から、年度と帯の列は `tabular-nums`。
- 出すフォルダか `index.html` が symlink（junction も）なら書かない。書くときは一時の名前で書いてから置き換える。
- 終わりの値：すべて ✓ なら 0、✗ があれば 1（ページは書く。✗ は集計に入れない）、台帳を読めない・書けないときは 2。Pages のワークフローで 1 を止めるかどうかは、ワークフローの側で決める。
- 会期中の台帳は架空の施設だけなので、【架空】はいつも出す（本物の施設を受けるときは、この表示を決め直す）。

## 7. 架空の 10 施設の束（台帳のデモ）

正解の世界：工場の `samples/factory/ledger_worlds.py` が、`world/ledger-facilities.json` に書いた差（乱数の種・名前・業者・処理能力・人が答える見え方・設置の年のずらし・外す機器・周期と人数の変更・足す取替）を、fictional-1（ストーカ式 2 炉）か fictional-2（流動床式 1 炉）の決まりに当てて、`samples/truth/waste-incineration/ledger-01`〜`ledger-10` の `world.json` を組む（資料は書かない。欠けは入れない。もう一度走らせると同じバイト列）。名前と業者は造語で【架空】つき。

| 見え方（人の答え） | 施設 | 全国の表の k |
|---|---|---|
| ストーカ・200〜400 t/日・発電あり・搬出・単年度 | ledger-01〜07 | 38 |
| ストーカ・100〜200 t/日・発電あり・搬出・O&M | ledger-08・09 | 32 |
| 流動床・100〜200 t/日・発電なし・搬出・単年度 | ledger-10 | 11 |

束：`node scripts/ledger/build-bundles.mjs --out <出す台帳のリポジトリの根> --rejects <外れた束のフォルダ> [--month 2026-11] [--state <状態のフォルダ>] [--ledger-json <前の ledger.json>]`

- 取り込みを通さず、正解の世界から直接書いた計画（`scripts/ledger/truth-plan.mjs`。まとめ工事は資料と同じに 1 つの作業にまとめる）を、本物の `previewBundle`・`sealBundle` に通す。固有名詞の網も本物（施設名・業者・計画の全部の文字列。置き場所の道は台帳で見える `ledger/bundles/<鍵ID>`）。
- ledger.json（台帳の決まり。欄は間隔・工数・日数）と各施設の鍵は、走らせるたびに作る。秘密鍵（PKCS#8 の PEM）と、施設と鍵の対応（`manifest.json`）は状態のフォルダ（既定は OS の一時のフォルダ）にだけ書き、最後にその道を出す。出す台帳には ledger.json と束しか書かない。
- 前の ledger.json を `--ledger-json` で渡すと、管理者の鍵を作らずにその決まりで束を作る（台帳 ID と決まりのハッシュが前と同じになる）。
- 書いたあと、受け手と同じ関数で確かめ（10 件 ✓）、PR の本文の文（状態のフォルダの `PR-facilities.md`）を書く。
- サイトの集計では、似た施設 7 の節に中央の帯（n 7）・幅の帯（取替 n 4）・x（取替 n 2）がどれも出る。

わざと外れた束（PR で Actions が理由つきで ✗ にした記録を残すため）。どれも新しい鍵の連番 1 で、道と鎖は正しく、本物の署名の関数（`signBody`）で署名してある。外れは中身だけ。封（`sealBundle`）はこれらに署名しないので、ledger-01 の束の body を書き換えてから署名した。それぞれ `<外れた束のフォルダ>/<名前>/ledger/bundles/...` と、PR の本文の文 `PR.md`（作る側のセッションが架空の束で出したものだと書く）：

| 名前 | 書き換え | 受け手と同じ関数の理由 |
|---|---|---|
| `kBelow5` | 見え方を、全国の表で 3 施設しかない組（ストーカ・100〜200 t/日・発電あり・セメント固化・単年度）にし、送る側の k も数え直しと同じ 3 にした | `k.belowMin` だけ |
| `costField` | 塊に `"cost": "1,200,000円"` を足した | `shape.type`・`freeText`・`money` |
| `facilityName` | body に架空の施設の名前の欄を足した | `shape.type`・`freeText` |

## 8. 束を出す（`ledger submit`。人だけ）

使い方は `moyai ledger submit --bundle <署名済みの束> --repo <台帳のリポジトリの clone> [--base main]`（人が端末で打つ）。

- 標準入力が端末でなければ断る（終わりの値 3）。AI のシェルからは、見張りのフックも止める。
- 束を、clone の `--base` の枝の木に足したときに受け手と同じ関数で ✓ になるかを確かめる（鎖が続かない・もうある・✗ なら 1）。
- 一時の索引に base の木を読み、束の blob を足して commit を 1 つ作り、枝 `moyai/bundle-<鍵ID>-<連番>` にする。作業の木と索引は変えない。
- PR の本文（鍵・指紋・連番・ハッシュ・見え方・塊の数。施設の名前は無い）を一時のフォルダに書き、`git push` と `gh pr create` のコマンドを出す。走らせるのは人（MOYAI は送らない）。PR を出す GitHub のアカウントが誰にでも見えることを必ず知らせ、台帳専用のアカウントを勧める。
