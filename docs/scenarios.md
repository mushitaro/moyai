# シナリオテスト：A〜E の「完成」を言う試験

運営者の目標（2026-11-12）：「A〜E の完成度を 100% にし、シナリオテストで完全合格する」。
この文書は、何が通れば「完成」と言えるかを決める。柱の中身は `docs/roadmap.md`、回し方は `docs/autonomy.md`。
完成は、下の全部が「合格」のときだけ言う。1 つでも「未確認」「待ち」が残れば、完成とは言わない。

- **自動**：`npm run scenario` が走らせる（CI の `scenario` の仕事でも走る）。結果は `eval/scenario/result.md`（手で書かない）。
- **実機**：運営者の PC（M-PC3、Windows・Claude Desktop）で、統括が手元のセッションから走らせる。結果は同じ表の「実機」の列に、日時と版（コミット）を添えて書く。運営者の目が要る段は「運営者の目」と書く。
- 数は測った値だけ。測っていないものは「未確認」。

## S-0 初めての人の通し（全部の柱をまたぐ）

M-PC3 の Claude Desktop の Chat で、次を会話だけで進め、人が押すのは画面の主ボタンだけ。

1. 「MOYAI をインストールして」→ 版ごとのフォルダに入り、Desktop を開き直すと MOYAI のツールが出る。
2. 「デモして」→ デモの施設で星取表ができる。
3. 業種のパックが無い施設の資料のフォルダを渡す → 初めて読む手順（1 年分 → Skill → 残りの年度）で計画ができる。
4. 確定のシートで受け、署名して確定する。
5. 出力（Excel）を主ボタン 1 つで落とし、Excel で開いて読める（運営者の目）。
6. 共有（共有フォルダ）を主ボタン 1 つで出す。
7. main が進んだあと、誰も頼まずに、次に Desktop を開くと新しい版になっている。

自動の代わり：`tests/demo/walkthrough.spec.ts`（MCP の SDK が Claude の役。ubuntu と windows の CI）。

## S-A 取り込みの精度

**物差しのサンプルは運営者の承認が要る。** 2026-11-13、運営者が旧サンプル（`samples/waste-incineration` の 11 施設）を「ファイルの形がほぼ同じ」として不合格にした（mushitaro/moyai#111）。A1・A1b・A3 は、運営者が承認した新しいサンプル（11 施設とも違う独特の形）で測ったときだけ合格にする。旧サンプルでの数は「旧」として残すが、合格の根拠にしない。新しいサンプルの最初の測りは、読み手を凍結して 1 回だけ行う。

| 印 | 合格の条件 | 道 |
|---|---|---|
| A1 | 物差し（`eval/bench/waste-incineration/`）で、11/11 施設で計画ができ、開いたままの問いが 0。⑥ と ③ が前の記録より下がらない（`compare.mjs --strict`） | 自動 |
| A1b | 同じ物差しで、施設ごとに：人に聞く問い（⑤）が 50 以下、③ 読み取りの正しさが 80% 以上、⑥ 取り戻せた割合が 70% 以上。計画が「できた」だけでは合格にしない（人が何千も答える・読み違いの多い計画は、使えない） | 自動 |
| A2 | 新しい見ていない様式（`docs/plan.md` §2.6：凍結 → 別の書き手 → 1 回だけ測る）で計画ができる | 自動（1 回だけ） |
| A3 | 初めて読む物差し（`first-read/`）で、年度ごとの資料のある施設すべてで計画ができる。施設ごとに、1 年目の問いが 50 以下・③ 80% 以上・⑥ 70% 以上（パックありの A1b と同じ）・人に聞かずに決めた答えの間違いが 0・残りの年度で、1 年目に見た問い（同じ問いで、正しい答えも 1 年目と同じもの。物差しの (a)）が 0。同じ問いでも正しい答えが年度ごとに変わる問いと、1 年目に無かった問いは、聞くのが正しい（(b)。数えるだけ）（#67） | 自動 |
| A4 | S-0 の 3 が M-PC3 で通る | 実機 |

## 結果の表

`eval/scenario/result.md` に、印ごとに「合格・不合格・未確認・待ち（誰の何を待つか）」と、版（コミット）と日時を書く。`npm run scenario` が自動の列を書き、統括が実機の列を書く。

- ランナーは `scripts/scenario/`（判定は `marks.mjs`、走らせるのは `run.mjs`）。新しい試験は作らず、物差し・e2e・vitest を呼ぶだけ。実機の列は、書き直しても前の字を残す。
- この PC で全部：`npm run build` のあと `npm run scenario`（物差し・台帳の試験・e2e と walkthrough を Chrome で。D3・E2 は `GH_TOKEN` か `GITHUB_TOKEN` があるときだけ読む）。
- CI：`e2e`（ubuntu・windows）が e2e と walkthrough を走らせて数を渡し、`scenario` が表を仕事の要約とアーティファクト `scenario-result`（result.md。実機の列はリポジトリの表から写す）に書く。リポジトリの `eval/scenario/result.md` は、ある回の結果をそのまま置いたもの（版・日時・走らせた所が表の頭にある）。入れ直すのは、main の CI の回の `scenario-result` をそのまま置くか、手元で `npm run scenario` を走らせたとき（どちらも手で字を直さない）。`scenario` の仕事はランナーが走りきれば緑で、合否は表の字（不合格の印があっても main を赤にしない）。
- D2 の `claude-code.spec` は、ふだん（CI）は代わりの台本（`tests/helpers/claude-standin.mjs`：本物と同じ引数・同じ `.mcp.json`・本物の中継で、判断だけを台本が決める）が Claude の役をする。本物の Claude Code での通しは `MOYAI_CLAUDE_E2E=1`（使用量を使う。M-PC3 で、実機の列に書く）。表の D2 の根拠に、どちらで走ったかを書く。
- `template-mcp.spec` は、運営者の資料がその PC にあればそれで、無ければ同じ形の架空の資料（入れ子の縦の結合と末尾の集計のある様式・fictional-1 の 9 本。計画ができたことも確かめる）で走る。
- CI の `scenario` の仕事は github.token で Issue を読む（D3）。E2 は、main への push の回だけ、同じ回の仕事の結果で決める（PR の回は未確認）。手元では GH_TOKEN か GITHUB_TOKEN が GitHub に通るときだけ読む。
