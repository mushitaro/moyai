## 2. 順と、その理由

1. **土台（E の一部）**：物差しと退行の検査を先に置く。A も C も、これが無いと良くなったかを言えない。
2. **A（取り込み）**：運営者の最優先。物差しの穴（下の A-1）を先にふさぐ。穴のある物差しで読み手を直すと、物差しに合わせた直しになる。
3. **D の 1 段目と B の直し**：A と触るファイルが重ならないので並べて進める（並行は 2 本まで）。
4. **C（進化の輪）**：A で物差しが信用できるようになってから、フィードバックをつなぐ。
5. **B の配置・D の作り直し・C のアプリからの書き出し**：運営者の判断が要る。判断が来たら進める。待つ間は止めない。

## 3. 柱ごとの中身

### A. 取り込みの精度

- A-1 物差しの穴：工場 v2 の正解を写す道具（`tests/heldout/v2.ts`）は出来事だけを写す。星取表のある施設で ③ が 0% と出るのは、読み手ではなく物差しの穴。印と機器も写す。写真だけで止まる施設（しらかば野）の扱いも決める。
- A-2 「1号炉定期補修工事」のような、機器の欄に書いた工事の名前の行き先（eventAssetOne が 46 問開いたまま）。
- A-3 同じ名前の機器の結び（assetLinkOne 46 問：かえで原・もみじ台・つばさ台）。答えれば読める星取表に、最初から「参考として外すか」を聞く所（つばさ台）。
- A-4 審査のあとに回したもの：計画の ○ と実績の ● が別の行に分かれる・報告書 PDF の折り返す表・1 頁 1 機器のカード・工程表の合計の行・号炉の書き方の語を Skillパックへ・作業の名前の「予:」・見出しの切れ端。
- A-5 新しい見ていない様式（`docs/plan.md` §2.6 の手順。凍結 → 別の書き手 → 1 回だけ測る）。
- 直し方の決まり：資料 1 つに合わせた継ぎはぎをしない。業種の語は Skillパック（2 段目）へ、どの業種にも当たる手がかりは標準へ、施設だけの読み方は 3 段目へ。

### B. 共有台帳

- B-1 受け口の点検と直し（済。11-10）。
- B-2 配置の前に運営者が決めること：受け口のトークンが main に直接書けないようにする道（別の台帳のリポジトリ／main のルールセット／別のアカウント）、Cloudflare のアカウントと費用、開いた PR の上限（今は全部で 20・同じ鍵で 1）。
- B-3 配置のあと：本物で 1 本通す試験、画面の言葉の確認、取り下げのボタン、台帳のサイト（Pages）。

### C. Skill の進化

- C-1 入口：Issue の型「読み方のフィードバック」（行の値を書かない）。ルールの案は `moyai.reading/0`（3 段目の rules.json と同じ形）。
- C-2 評価：`node scripts/bench/pack-candidate.mjs <パック> <案.json>` が、今の値と案の値を比べて、退行あり・良くなった・差なしを数だけで出す。PR に packs/ か src/import/ の変更があれば CI が同じ比べをする。
- C-3 案：自律のセッションが、退行のない案を PR にする（packs/ の変更は案。マージ＝昇格を決めるのは人）。
- C-4 アプリからの書き出し（GitHub のアカウントが無い人のフィードバック）：何を PC の外へ出すかを広げるので、運営者に聞いてから。
