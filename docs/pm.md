# MOYAI の統括の決まり

2026-11-05 に運営者が、開発の全体統括（PM）のセッションを置いた。それまで Dev が開発マネージャーと統括を兼ねていて負荷が高く、運営者の判断も多かった。PM は各セッションと運営者の橋渡しをし、整合と分担を見て、運営者の判断の量を減らす。

**2026-11-05 の夜、運営者が統括を Dev に戻した。** PM のセッションは、受け取る 1 通ごとに大きな文脈を読み直す作りで、使用量を食いすぎたため。下の決まり（課題台帳は 1 つ、出し方は Wire、判断の問いは統括へ、運営者に聞くのは §4 だけ）は Dev が引き継ぐ。表の「PM」は「統括（Dev）」と読む。各セッションの報告は区切りごとに 1 通だけにし、確認の返事はしない。

**API のキーの渡し方（運営者の決定、2026-11-05）**：キーはユーザー環境変数 `ANTHROPIC_API_KEY` に置き、Claude Code 自身の環境には入れない。API を呼ぶコマンドは `node scripts/with-api-key.mjs <command> [args...]` で走らせる（スクリプトが中で読み、子プロセスにだけ渡す。値は表示も記録もしない）。例：`node scripts/with-api-key.mjs node .cache/review/review.mjs`。

## 1. 役と分担

| セッション | 役 | 聞く先 | 報告の先 |

| PM | 全体の統括。課題の順と分担。運営者には「決めたこと」と「運営者にしかできないこと」だけを渡す。日誌の統括の節 | 運営者（まとめて 1 回） | 運営者 |

| f3-eval（Dev の子） | F3 Skill の採点（API を使う） | PM | PM |

Design と Logo は仕事を終えている。

## 2. 流れ

- **課題は 1 つの台帳に集める。** Architect が持つ。Architect の A〜F、Db の重・新、Wire の直し、CI の監査の指摘、レビューの指摘を、重ならないように並べる。順は PM が決める（Architect の推す順を基本にする）。Db と Wire は Dev へ直接は渡さず、台帳へ入れる（小さな画面の直しは Wire から Dev へ直接でよい）。
- **判断の問いは、まず PM へ。** PM は `docs/plan.md`・§7 の答え・運営者の判断の傾向から決められるものは決め、日誌に「PM が決めた」と書く。決められないものだけ、運営者に 1 回でまとめて聞く（選べる道・それぞれで起きること・推す道と理由。`AGENTS.md`）。
- **運営者にしかできないことは、PM が一覧にして日時つきで頼む。** 外へ出る操作（GitHub・YouTube・提出）、本人の言葉（冒頭の一文、声）、実機の目（Excel の見やすさ、Claude Desktop）。
- **セッション間の連絡は短く。** 1 通に、したこと・確かめたこと（5 つの分け方）・次・聞きたいこと。コミットのハッシュと写しの場所を添える。

## 3. PM が運営者に聞かずに決めること

- 作業の順、分担、並べる本数。
- worktree の枝を main に入れるか（CI が緑で、`src/` の約束を破らないもの）。
- 試験の範囲、凍結の日時（計画 §6 の目安の中で）。
- 出し方の細部は Wire の判断を、設計の細部は Architect の判断を採る。
- API の費用の、配分の中での使い方（`config/models.json`）。
- 決めたことは日誌に書き、運営者が見て違えば言い直せるようにする（黙って決めない）。

## 4. 運営者に聞くこと（これだけ）

- 運営者の画面の約束（星取表・検問所）を変える。共有で出す欄を広げる。範囲を大きく削る。§7 の答えを変える。
- 本人の言葉：動画の冒頭の一文、声の収録。
- 外へ出る操作：GitHub の OAuth App の登録、公開の台帳の PR のマージ、YouTube の公開、提出。
- API の費用の止める額を越えること。

## 5. 運営者の判断の傾向（要点）

過去の答えから読み取ったもの。細かくは統括のメモにある。迷ったら、この傾向で決め、日誌に書く。

- **決めるのは人、作業は AI。** 確定・送る・承認は人の署名。AI が決めたものは案として並べ、人が受けるまで決まらない。
- **引き算。** 画面に説明を置かない。1 画面 1 目的 1 操作。色は墨と朱。
- **正直に。** 測っていない数字を出さない。動いていないものを動いているように見せない。未確認は未確認と書く。
- **合言葉は嫌う。** 守りは PC のアカウントと署名で。面倒な手順を増やさない。
- **現場の形。** 試験のために構造化した資料はだめ。汚い資料をそのまま読み切る。読み手の継ぎはぎ（パチ当て）はしない。詰まったら会話で読み方を決めて Skill に残す。
- **計画に書いてあることは聞かない。** 書いてあるとおりに進める。聞くのは計画が運営者に委ねたことだけ。
- **推す案を採ることが多いが、自分で決め直す。** 複数案を出すと、どれでもない形（施設の鍵、マジックリンク）を自分で出すことがある。
- **捨てずにやり切る。** 締切までに手放すものを先に決めない。間に合わなかったものは測った値のまま未実装と書く。
- **業界構造から語る。** 動画・README は課題の本質（持ち主・メーカー系列の随意契約・O&M）から入る。
