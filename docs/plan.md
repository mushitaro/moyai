## 0. 軸

保全の記録は、施設ごとに項目も書き方も深さも違います。だから、似た施設どうしでも並べて比べられません。MOYAI は、記録の一つ一つを、国の手引きが業種ごとに示す設備・機器のリスト（共通の設備項目）と 4 つの作業の属性の組に当てます。当てた記録は星取表の同じ行に入るので、自分の施設の行の下に似た施設の行を並べて、周期・工数・日数を比べられます。最初の業種はごみ焼却で、ここを深く作ります。ほかの設備は、その設備の公のリストを入れたパック（データ）を足すだけで、同じ作りのまま扱えます。

1. **共通の設備項目は、公のものを使う。** ごみ焼却は、環境省『廃棄物処理施設長寿命化総合計画作成の手引き（ごみ焼却施設編）』（令和 3 年 3 月改訂）の表Ⅱ-4「主要設備・機器リスト例」【確認：印刷頁 29、PDF の 37 枚目】。作業の属性は、点検・分解整備・更新・基幹改良。項目は 2 段で持ち、1 段目は業種の公の項目、2 段目は業種を越える機器の種類（20 種）。2 段目があるので、焼却施設の誘引通風機も、下水の送風機も、ビルの空調機も、同じ「送風機」の行に入る。記録をどの項目に当てるかは AI が案を出し、人が決める。項目を自分たちで作らないので、どの施設とも同じ行で比べられる。
2. **横串は星取表で刺す。** 行は項目 × 作業の属性、列は年度、印は実施と計画。似た施設（ごみ焼却では炉の型と処理能力の帯が近い施設）は匿名の札で並び、周期・工数・日数の帯と統計の行が付く。費用は出さない。
3. **ごみ焼却で作り込み、広げるときはパックだけを足す。** し尿処理のパックを足したコミットで `src/` が変わらず、取り込みから星取表まで通ることを試験で見せる。設備の地図（A 市町村の環境〜H 交通）の全行は、名前と出どころだけのパックとして画面に並べる。

**この軸が解く課題：似た施設と比べられない。** 市町村の環境局は全国の似た施設と、プラントメーカーの保全子会社は自社の納入先や他社のプラントと、民間の O&M 事業者は入札の対象に似た施設と比べたい。けれども相手の履歴は、ほかの誰かの台帳の中に、ほかの書き方で入っていて、共有の場もありません。市町村はごみ焼却とし尿処理を一緒に持ち、保全子会社は焼却・し尿・下水・水を横に請け負うので、業種を越えて同じ行で比べられることが効きます。

| 機能 | 軸での役目 | 会期中の扱い |
|---|---|---|
| F1 取り込みとパック | どんな資料（Excel・CSV・PDF・写真）も読み切り、記録を共通の設備項目 × 作業の属性に当てる。業種はパックで足す | 中心。作る |
| F2 共有（輪と公開の台帳） | 比べる相手（似た施設）を集める。秘密は出さない | 山場。作る |
| F3 Skill の採点 | 当てはめと判断の質を、同じ問題で測って上げる | CLI とコードの採点が本線 |
| F4 手元のモデル | 当てはめを、データを外に出さずに手元でする | 構想の図と絵だけ（「構想」の札） |

この文書・README・動画は、共通の設備項目 → 横串の星取表 → ごみ焼却で作り込み、ほかへ広げる、の順で語ります。合言葉は「知恵は出し合う。秘密は出さない。」

## 1. 使う人と、画面の流れ

| 使う人 | 比べたいもの | 使う場 |
|---|---|---|
| 市町村の担当者（いちばんのニーズ） | 自分の施設の周期・工数・日数を、全国の似た施設と | 公開の台帳 |
| 保全子会社 | 自社の納入プラントどうし。O&M に変わるときの工数と日数の見込み、新設の 10 年計画（費用は出さない） | 自社の輪＋公開の台帳 |
| O&M 事業者 | 入札の対象に似た施設、自社が請け負う施設 | 公開の台帳＋自社の輪 |
| 経験の浅い後継者 | 前の担当者が決めた理由 | 差分レポート（一言の理由つき） |

ある担当者の流れ（画面の名前は【】）：

1. 【取り込み】に、1 つの施設の資料をまとめて入れる（星取表の Excel、委託先の報告書の PDF、作業日報の CSV、日常点検表の写真）。写真は、AI クライアントに渡ることをファイルごとに許してから読ませる。
2. MOYAI が全部を読み、決まらない所だけを、同じ書き方の行をまとめて既定の答えつきで聞く。答えは「決定」として残り、取り消せる。どのセルも「データ／外した（理由）／未解決」のどれかに数えられ、未解決が 0 になったときだけ計画ができる。
3. 【星取表】で、自分の台帳の段の行と、共通の設備項目の行（項目 × 作業の属性）を切り替える。共通の行では、輪と公開の台帳から届いた似た施設が自分の行の下に並ぶ。立場（市町村／保全子会社／O&M）を切り替えると、並ぶ集まりだけが変わる。
4. 【検査】が、パックの基準から外れた所を、根拠の数字と出典つきで出す。いつも「自己点検であって、審査の判断ではない」と添える。
5. 人が周期を直し、一言の理由を書いて確定する。差分レポートと、人が見る様式の Excel が残る。前の版は消えない。
6. 【検問所】で「相手から見たあなた」を確かめ、合言葉で束に署名して、輪か公開の台帳に出す。

## 2. 機能定義

### 2.1 共通の設備項目と作業の属性

- **1 段目**（業種の公の項目）は、パックの `common.json` に、出典の表と頁つきで持つ。ごみ焼却は表Ⅱ-4 の設備と機器をそのとおりに持つ（炉の型ごとに分かれる機器、灰出しの溶融設備の有無で分かれる項目も表のとおり）。
- **2 段目**（業種を越える機器の種類）は `packs/_kinds/kinds.json` の 1 つだけ。20 種（ポンプ・送風機・圧縮機・クレーン・コンベヤ・電動機・弁・配管・タンク・熱交換器・ボイラー・受変電・盤・計装・昇降機・空調、と運営者の決定（2026-11-03）で足した炉・集じん装置・発電機・破砕・切断機）を平らに持ち、会期中はこれ以上細かく分けない（分けるほど当てはめの迷いが増え、業種をまたぐ行がまばらになるため）。4 種を足したのは、16 種ではごみ焼却の 35 項目のうち 27 が当たる種類を持たず、横串の行に並ばなかったため。名前は法令が名指しする設備と公の手引きの名前から取り、種類ごとに出典か「自分で決めた理由」を書く。協会・JIS・ISO の分類の名前は写さない。1 段目のどの項目にも、2 段目の種類か「当てはまらない（理由）」を付ける。
- **作業の属性**は、コードが `INSPECT`・`OVERHAUL`・`REPLACE`・`UPGRADE` の 4 つ。画面に出す名前（点検・分解整備・更新・基幹改良）は `packs/_kinds/work.json` の既定で、業種のパックが言い換えられる。`src/` にはコードだけを置く。業種の言い方（「定期整備」「開放点検」など）の読み替えはパックの語彙に置く。事後の修理は属性に入れない（記録には残す）。
- **当てはめ**：台帳の節（どの深さでも）→ 1 段目の項目、作業 → 作業の属性。AI は「この条件の節はこの項目」という規則（§2.13 の形）を案として置き、画面がそれを行に当て、当てた数とぶつかった数を AI に返す。人が画面で受けたものだけが決まった当てはめになり、共有にもそれだけが写る。決まっていない記録は「未当てはめ」の行に集め、件数を出す。
- 機器は**同一性の鍵**が同じときだけ同じ。名前が似ているだけではまとめない。鍵の無い資産は、人が決めるまで「未解決」。
- 分類コードの形は `^[A-Z]{2,4}(\.[A-Z0-9_]{2,16}){1,4}$`。頭の文字はパックが決める。

### 2.2 星取表（横串）

運営者の画面の約束を、細部までそのまま作ります。変えるときは先に聞きます。

- 階層はピボット表の表形式。段ごとに列を立て、上の行と同じ名前は空ける。帯の行や木の見出しは使わない。段の列は左に固定。
- 段の数と名前は計画が持つ（パックの段の名前は既定値）。3 段目は部位・系統（号炉ではない）。4 段（機器 › 系統 › 部位）にもできる。名前の無い段は「第 n 階層」。「共通」は 3 つの意味（系統に共通の部品／系統が合流して分かれる機器／施設全体の共通の設備）を分けて持つ。
- 畳む：段の列の見出しを押すとその段で畳み、畳んだ行にまとめの印（薄い色）と台数を出す。もう一度押すと開く。畳んだ深さはブラウザに覚える。畳んだ行をダブルクリックすると中の作業の明細。畳んだ行の印は消せない（消すときは開いて消す）。
- 行の切り替え：自分の台帳の段の行 ⇄ 共通の設備項目の行。共通の行では、似た施設を同じ行に並べ（§2.8）、未当てはめの記録を 1 行に集めて件数を出す。
- 期：年度（パックの始まりの月）と、その下の月。年だけの表と月までの表を切り替える。
- 行は平らにして `level` と `parentId` を持たせ、開閉は自前の状態で持ち、見える行だけを表に渡す。印は書式の関数と CSS のクラスで描き、セルごとに React の部品を持たない（数千のセルでも軽く動かすため）。セルの aria-label に階層の道を入れる。
- マウスを載せると「誰が・なぜ・前→後」。選んだ印の出どころ（どの資料のどのセル、写真なら画像のその位置。誰がなぜ変えたか）を横に出す。元の計画と調整後を切り替えられる。
- 周期で計画を引くダイアログ（「5 年ごとの 7 月」など）。文字の入力は Enter か F2 で編集欄を開いてから（IME の最初の 1 文字を落とさないため）。
- 表は AG Grid Community だけで作る。木の表示・行のまとめ・Excel の書き出しは Enterprise の機能なので使わず、上の自前の形と exceljs で作る。CI で、固定した依存の一覧（package-lock.json）に ag-grid-enterprise が無いことを確かめる（`scripts/check-deps.mjs`。別名で入れた依存も見る。npm ls の終了コードは版によって変わり、「見つからない」と誤りを見分けにくいため。日誌 2026-11-03）。

印と色（色だけに頼らず、どれも印か罫か見出しを持つ。色は CSS 変数の 1 か所）：

| 見せるもの | 印 | 色 | 理由 |
|---|---|---|---|
| 実施 | ● | 本文の色 | 色の無い印刷でも分かる |
| 計画 | ○ | 本文の色 | 同上 |
| 同じ年度に計画と実施 | ◎ | 本文の色 | 1 つのセルで両方を見せる |
| 変更（調整後） | 印の右肩の点＋セルの罫 | 橙 | 変えた所を色と形の両方で |
| 畳んだ行のまとめ | 薄い印＋台数 | 薄い灰 | 畳んであることが分かる |
| 要確認（写真から読んだもの） | 印の前の「?」 | 黄 | 人が画像と並べて確かめるまで |
| 似た施設の行 | 同じ印 | 青みの灰の背景、見出し「似た施設」 | 自分の行と混ぜない |
| 統計の行 | 帯の文字 | 灰、見出し「統計」 | 印ではなく帯で見せる |
| パックの基準 | 帯の文字 | 緑み、見出し「パックの基準」 | 出典つきの目安を統計と分ける |

### 2.3 ごみ焼却で作り込む（1）取り込み

**一つの施設の資料は、まとめて読みます。** 星取表には計画と実施の印しか無く、残りの履歴は報告書や日報に書いてあるからです。同じ作業がいくつかの資料に出てきたら、出どころをいくつも持つ 1 つの記録にします（機器・作業の属性・年度と日付・工数で結ぶ）。結べるか決まらないものは質問に回します。AI だけで結んだものは一覧に出し、人が受けるまで確定できません。どの資料にも書いていない履歴は、理由ごとに数えます。

層（同じ入力からはいつも同じ出力。AI が入るのは層 3 と、写真の読み取りだけ）：

| 層 | すること | 出力 |
|---|---|---|
| 1 原本 | 形式ごとの読み手（下）。層 2 から先は形式を知らない | どの形式も「セルの格子＋出どころ（ファイル・シートか頁・位置）」。読まなかった物は数えて台帳に残す |
| 2 構造 | 書き方によらず 1 つの木に落とす。名前の列の位置・頭の空白・字下げ・グループ・結合・太字が、行ごとに「何段目か」へ票を入れ、割れたら「疑い」。行の役割（題・凡例・見出し・親・データ・小計・合計・注記）を先に決める。くり返す領域（帳票の枚、続紙）を見つける | 木と行の役割 |
| 3 意味づけと決定 | AI が受け取るのは、要約・行番号つきの見本・凡例・注記・質問の候補だけ。不確かな所だけを聞く | 決定（同じ種類の行すべてに効き、取り消せる） |
| 4 当てはめと検算 | 元のセルを「データ／外した（理由）／未解決」に数える。小計・合計・番号の続きで検算する | 計画（base）か、作れない理由の件数 |

形式ごとの読み手：

- **Excel**（.xlsx・.xlsm）：値・表示の文字・数式・結合・メモ・行と列のグループ・非表示・字下げ・書式・罫線・印刷範囲・ウィンドウ枠・テーブルを全部読む。表示の文字は ssf で作る。exceljs は日付を Date で返すので、表示形式を当てる前に通し番号へ戻す（1904 年の基準も）。和暦の書式（`[$-411]`・`ggge`・令和）が ssf で出なければ、元号の表を一般の性質として `src/import/` に持つ。図形の文字・入力の規則・改ページは、zip の中の XML を数えて「読まない物」として台帳に残す。**数式があって計算済みの値が無いセルは、未解決に数える。**
- **CSV・TSV**：文字コード（UTF-8・BOM 付き・Shift_JIS／cp932）と区切りと囲みを判定し、判定の結果を台帳に残す。決まらなければ聞く。
- **文字のある PDF**：pdf.js の文字と位置から、罫線と位置で格子を組む。頁と座標を出どころにする。埋め込みの無い日本語の書体のために、cMap と標準の書体のデータを pdfjs-dist に同梱のフォルダに向ける（Node では legacy の build）。罫線の取り方は 6.4.299 で確かめて固定する。
- **写真・スキャン**（JPEG・PNG、文字の無い PDF の頁）：人が画面で［AI クライアントに渡して読む］を押した画像だけを、MCP のツール（§2.13 の `photo_transcribe`）で AI クライアント（Claude Code・Claude Desktop）に渡し、格子と、セルごとの位置と読めた確からしさを型で返させる。AI クライアントは利用者の契約の中で動き、MOYAI は API のキーを使わない（運営者の決定、§7）。作者は「AI（読み取り）」。**人が画像と並べて確かめるまで「要確認」に数え、計画を作らない。**
- `.xls`・`.doc` は「保存し直してください」と返す（受け付ける形式と読み手を一致させる）。

止める決まり：未解決・当てはまらない決定・意味の決まらない記号・要確認のどれかが 1 つでもあれば、計画を作らない。件数は保存したあとに数え、「入れた行＝取り込んだ数＋外した数（理由ごと）」を必ず出す。

最初から芯の形として扱い、工場でも最初から書き分ける書き方：1 つのセルに書いた年度の範囲や元号だけを 1 段にした見出しなどの和暦の年度、途中で変わる年度の帯、「〃」や空欄で「上と同じ」を表す列、字下げだけの 1 列、縦に結合した大分類、番号 1 / 1-1 / 1-1-1、名前の中の機器番号、1 シートに複数の表、途中で変わる見出し、表の下の凡例と ※ の注記、上に置いた合計、1 日 1 シートや 1 件 1 枚の帳票と続紙、頁ごとに見出しをくり返す PDF の表、実績の列と計画の列で同じ記号の意味が違う表、網掛けで意味を分けた表、自分の作業を持つ親の行。性質の試験も置く：備考の文の中の数を黙って値にしない（「次回は 3 年後」の 3 を周期にしない）、日付に見えない書き方（「昭和 63 年度末」など）を日付と決めつけない、行の役割を黙って変えない（合計を小計に、注記をデータにしない）。

### 2.4 ごみ焼却で作り込む（2）芯のデータの形・パック・検査・きっかけ

**芯のデータの形**（どの業種でも同じ。業種で変わるのはパックだけ）：

- **施設**：計画の単位。年度の始まり（公共は 4 月を既定、民間は取り込みのときに聞く）、規模、該当する法令の印、架空の印、全国の表に載る施設か（人が答える）。
- **資産の節**：同一性の鍵、表示の番号（タグ）、名前、段（段の数は可変。段の名前と鍵はパックが宣言する）、分類コード、共通の設備項目（当てはめの作者と根拠つき）、仕様（項目と値）、有効期間（設置・撤去・取替）、系列。
- **作業**：種類、保全方式（時間基準・状態基準・事後）、対象の資産（多対多）、きっかけ、根拠の検査 ID、外注先（架空）。上位の作業が下位を兼ねる入れ子、範囲のタグ（U-2504A/D）と列挙のタグ（T-2702,2752）も 1 つの作業で表す。
- **作業明細**（印 1 つ）：計画か実績か、開始日と終了日（時刻帯の無い文字。年度だけでもよい）、費用（欄として持つが、共有しない）、工数、結果（判定の尺度の値と測った値）、実施者（「個人」の印。共有では欄ごと出さない）、出どころ、根拠と作者。点検・診断・措置は別の行にし、前回の値を残す。
- **計量値**：資産か施設ごとの日付つきの系列。減る値は「疑い」にする。

**パック**＝1 業種 1 フォルダのデータ＋Skill の文。実行時にスキーマで検証し、通らないパックは読み込まずに理由を画面に出します。

```
packs/<pack-id>/
  pack.json     版・名前・群・確かめた度合い・年度の始まり・段の名前・同一性の鍵・判定の尺度・sharing（on/off）
                比べる軸とその順（profile）・全国の表の出どころと列の読み方・単位（t/日、kL/日 など）
  common.json   1 段目の項目（出典の表と頁）、2 段目への対応、作業の属性の言い換え
  world.json    工場の世界の決まり（作業の順・契約の期間・全休止・法令の周期・粒度・呼び名の揺れ・書き漏れの割合）
  vocab.json    分類コードと名前・上位の分類・名前に出る語・周期の語の読み替え・取り込みの手がかりの語
                共有の公開語彙（分類ごとの implies と universal。出典つき）

  sources.json  資料の一覧（名前・発行元・URL・取得日・利用条件・状態・照らした頁や条・照らした者）
  SKILL.md      AI の読み方と答え方（日本語。業種ごとに一次資料から新しく書く）
  expected/     見本の計画に対する期待する検査の結果
  national/     全国の表から数だけを取り出した表（scripts/ が作る。施設名を持たない。出典と「加工した」ことを書く）
```

- 確かめた度合いは 4 段（`原典照合済`／`要約のみ`／`未確認`／`プレビュー`）で、画面と検査の結果に必ず出す。原本で照らしたものだけを `requirement` にする。ごみ焼却のパックは最初に照らす。
- **業種の語は、すべてパックに置く。** 書類の一般の手がかりの語（小計・合計・凡例・続き など）も `packs/_cues/` のデータに置く。コードには一般の性質（結合・字下げ・太字・行のグループ・値の型・和暦）だけを置く。画面に出す業種の言葉（作業の属性の名前、単位、群の名前、原子力を作らない理由など）も、パックと `packs/_kinds/` から読む。試験は、業種のパックの `vocab.json` と `common.json` にある 2 文字以上の語を NFKC にして、`src/` の文字列とコメントから部分一致で探し、1 つでも出たら落とす。除く語は理由つきの一覧にしてコミットする。
- 検査の種類はコードの閉じた一覧（本線の 8 種：`interval_max` 間が空きすぎていないか・`next_due` 次回が期限の内か・`coverage` 対象のすべてに作業があるか・`record_fields` 記録に決められた項目があるか・`followup` 判定のあとに措置の計画があるか・`plan_fields` 計画表に決められた列があるか・`plan_horizon` 計画が決められた年数分あるか・`scale_valid` 判定の値が尺度に属するか）。パックが書くのは、どの種類を、どの項目に、どの値で当てるかだけ。種類を足すときはコードと試験を足す。
- 検査は純粋な関数（同じ計画と同じ基準日なら同じ結果）。結果は `met / notMet / notApplicable`、根拠の数字、例（10 件まで）、件数、出典、水準（`requirement` 法令・補助の要件／`recommendation` 要領・ガイドラインの例／`app` アプリの目安）、閾値の出どころ（出典／アプリの目安）。承認の記録が無い延長は `notMet`。AI は数字を丸めず言い換えず、出典を添えて説明するだけ。検査を直すのは人で、直したらパックの版を上げる。
- **精密機能検査**：廃棄物の処理及び清掃に関する法律施行規則（昭和四十六年厚生省令第三十五号、法令 ID 346M50000100035）の第 5 条は、ごみ処理施設とし尿処理施設の管理者に「定期的に」精密な検査をするよう求めるだけで、年数を書いていない【確認：e-Gov の 2026-09-16 施行の本文。このセッションが 2026-11-03 に照らした】。年数は「廃棄物の処理及び清掃に関する法律の運用に伴う留意事項について」（昭和 46 年 10 月 25 日 環整第 45 号 厚生省環境衛生局環境整備課長通知）の第三の 11「規則第五条の精密機能検査は三年に一回以上行なうこと。」にある（https://www.env.go.jp/hourei/11/000510.html 。【確認：運営者の別のセッションが 2026-11-03 に照らした。パックに入れるときに、このセッションでも原文を照らす】）。課長通知は行政指導なので、この検査は水準を `recommendation`、閾値の出どころを出典（3 年）にする。検査の細目は昭和 52 年 環整第 95 号 別紙 4「精密機能検査要領」で、頻度はここには無い。総務省の資料（https://www.soumu.go.jp/main_content/000401742.pdf ）は、実施の状況を示す二次資料として添える。同じ条がし尿処理施設にも掛かるので、し尿処理のパックも同じ種類の検査を自分の出典で持てる。動画では、表Ⅱ-4 の `coverage` とこの間隔の検査を映す（どちらも出典を照らし終えてから）。
- ごみ焼却の検査は 5 件以上。候補：表Ⅱ-4 にあるのに計画に無い機器（`coverage`）、精密機能検査の間隔（`interval_max`、`recommendation`）、健全度が悪い判定のあとに措置の計画が無い（`followup`）、機器別管理基準に保全方式・周期の列が無い（`plan_fields`）、計画の年数が足りない（`plan_horizon`）、記録の必須の項目の欠け（`record_fields`）、健全度の段の外の値（`scale_valid`）。手引きの計画の要件と健全度の段の名前と数は原本で確かめてから `requirement` か `recommendation` にし、確かめられなければ `app` にする。
- **きっかけ**は枝の集まり（暦・計量値・状態・出来事）と、まとめ方（早い方／全部）・起点（前回の実施・基準日・使用開始）・前後の窓・初回だけの周期・休止を数えない上限・幅のある周期・承認による延長と上限。周期の書き方の揺れ（「6Y」「130M」「5C」「毎回」「隔回」）は、パックの語彙で読み替える。計量値の枝の次回は、直近 12 か月の増え方から見込み、根拠に「見込み」と出す（記録が 2 点に満たなければ「計量値が足りない」に数える）。年度だけの印は年度の差で数え、根拠に「年度の粒度」と書く。ごみ焼却では、号炉ごとの運転時間と暦の早い方で次回を出す。どの群の周期でも書けることは、鉄道（km）・火力（運転時間と起動回数）・船舶（前後の窓）・昇降機・消防（法定の周期）の性質試験で確かめる（パックもサンプルも作らない）。

### 2.5 ごみ焼却で作り込む（3）サンプルの工場

数十行のデモはアプリを悪く見せます。正解の世界を 1 つ作り、そこから現場の形の汚い資料を書き分けます。

- 生成器は Python 3.12＋openpyxl（版を固定）。PDF は LibreOffice の headless で帳票を書き出す（並べて動かすときは、呼ぶたびに `-env:UserInstallation` で別の設定を使う）。写真は、PDF の頁を pypdfium2 で画像にし、傾き・影・ぼけ・手書きの丸やチェックを Pillow で足す。アプリ（TypeScript＋exceljs）と読み手が別なので、原本の漏れを比べられる。出力はコミットするので、審査員は Python なしで試せる。
- 正解は生成器が自分で書いた中身から書き出し、試験だけが読む。AI には渡さない。乱数の種と物語の「今日」を固定し、作り直すときは版を上げる。
- 小計・合計は数の値で書く（openpyxl の数式には計算済みの値が入らないため）。数式の行を試すときだけ LibreOffice で再計算してから保存し、再計算済みのものをコミットする。
- 汚さは 3 種類を別々に記録する：資料の汚さ（取り込みが読み切るもの）、計画の欠け（検査が見つけるもの。検査 ID とひもづけ、5 件以上）、資料ごとの書き方の違い（同じ作業を、呼び名・粒度・日付のずれで書き分け、どの資料のどの行が同じ作業かを正解に書く）。書き漏れと年度の書き間違いの割合（どちらも数 %）は世界の設定に書き、正解に記録する。
- 作業の組み方は世界の決まり（`world.json`）に持つ（上流から下流への作業の順、業者ごとにつながった契約の期間、全休止の整備の前後、法令の点検の周期、資料ごとの粒度の違い）。業種を足すときに生成器のコードを足さない。
- 工数（人・日）と日数（工期）を作業ごとに書く。号炉ごとの定期整備と系統の整備、全休止の期間、基幹改良の工期と工数は世界の決まりから作る。書き方は揺らす（人・日、人工、延べ人数、時間、日数だけ・期間だけ）。複数の機器をまとめた工事の行も入れる。
- どの業種にも使う汚さの部品：2 段の見出し（年度の下に実績／予定）、隠した古い年度の列、和暦と西暦の混在と年号の切り替え、〃 と空欄、半角カナ、括弧の全角・半角、セルの中の改行、メモ、凡例と凡例に無い記号、小計と合計、範囲のタグと列挙のタグ、年で変わる様式、記号 ○●◎、号機・系列の書き方の揺れ、取替・撤去・新設を備考に書く、続紙。
- すべて架空。実在の施設 ID・施設名・登録番号・事業者名・公開資料の行の写しは作らない。施設の構成（炉の数・炉型・規模・年数）は、全国の焼却施設の表の分布から選ぶ（分布の値としてだけ使い、出典と「加工した」ことを書く）。有料の表の数値は使わない。どのファイルにも「【架空】」を、表題のセルとファイルの作成者の欄の両方に入れる。

**ごみ焼却の資料の組（決めた）**：作り込む施設は 1 つ（架空。ストーカ式 2 炉）。厚さは、機器が数百、作業が千を超え、契約が数百、10 年分以上。デモにも同じ厚さを使い、動画で引く行は手で見直す。

| # | 資料 | 形式 | 主な汚さ |
|---|---|---|---|
| 1 | 機器台帳（設備・機器・仕様・設置年） | Excel | 字下げの 1 列、番号 1 / 1-1、名前の中の機器番号、セルの中の改行、取替・撤去を備考に |
| 2 | 整備計画（星取表のシートと、長寿命化の計画の機器別管理基準のシート） | Excel | 2 段の見出し、和暦と西暦の混在、縦に結合した大分類、〃、隠した古い年度の列、凡例と凡例に無い記号、1 シートに複数の表、上に置いた合計 |
| 3 | 定期整備の工事報告書（号炉ごと・年度ごと） | 文字のある PDF | 頁ごとにくり返す見出し、続紙、帳票の中の明細と合計、工数と工期 |
| 4 | 委託先の作業日報（業務の仕組みからの書き出し） | CSV（Shift_JIS と UTF-8） | 1 日 1 行、半角カナ、括弧の全角・半角、まとめ工事の行 |
| 5 | 日常点検表（紙を撮った写真） | JPEG | 傾き・影・ぼけ、手書きの丸とチェック |

- 精密機能検査の記録は 2 と 3 に書き分ける（間隔の検査の材料）。
- 5 種にしたのは、星取表だけでは戻らない履歴（報告書・日報）と 4 つの形式を、1 施設でそろえられる最小の組だから。
- **深さと呼び名の違う 2 つ目の施設**：機器台帳と星取表を、段の数（2 段と 4 段）と呼び名を変えて、もう 1 つの架空の施設の分も書き分け、取り込みと当てはめまで通す（当てはめの試験の材料にし、輪の拠点の 1 つにする）。
- 輪のデモのほかの拠点と、公開の台帳の架空の 10 施設は、同じ工場が正解の世界から直接書いた計画を使う（取り込みを通すのは上の 2 施設だけ）。束は本物の写し取りと署名のコードで作り、架空の拠点の鍵は試験の道具が作る（秘密鍵はコミットしない）。このことは README にも書く。
- し尿処理は、架空の 1 施設と資料 2〜3 つ（星取表の Excel、機器台帳の Excel、点検の CSV）を工場から出す。ごみ焼却と同じ厚さのふりをしない。
- 縦の 1 本の小さなデータも、最初から工場（v0）で出す（手で作って捨てないため）。

置き場所：

```

samples/out/<pack>/<施設>/        生成した資料（コミットする）
samples/truth/<pack>/<施設>/      正解（試験だけが読む）
samples/facts/<pack>/<施設>/      別の読み手（openpyxl）が取った原本の事実（物差し ①）
```

### 2.6 取り込みの物差しと、見ていない様式の試験

| 物差し | 比べるもの | 目標 |
|---|---|---|
| ① 原本の漏れ | MOYAI の読み手の原本 ↔ openpyxl が取った事実 | 0 |
| ② 行き先 | 全セル ↔ データ／外した／未解決 | 未解決 0 |
| ③ 読み取りの正しさ | 記録 ↔ ファイルごとの正解 | 開発用で 100% |
| ④ 検査の正しさ | 検査の結果 ↔ 入れた欠け | 欠けはすべて notMet、誤検出 0 |
| ⑤ 聞いた数 | 読み切るまでの質問の数 | 記録し、版ごとに比べる |
| ⑥ 取り戻せた割合 | 正解の世界の履歴のうち、どこかの資料に書いてあるもの ↔ 計画に入った記録 | 100%（どこにも書いていないものは分母に入れず、理由ごとに数える。星取表だけで戻せた割合も参考に出す） |

- 最初の日から測り、`docs/trend.md` に日ごとの推移を、試験の実行から生成して残す。
- 「書き方の違い」として同じと見なす範囲（全角と半角、前後の空白など）は、物差しの側に一覧で小さく書く。
- **見ていない様式**（時刻の順で示す。締切の時点で非公開のものを残さない）：
  1. 開発用の Excel・CSV・PDF で ① 0・② 0・③ 100% に届いたら、読み手を凍結してタグを打つ（`reader-freeze-1`）。
  2. 新しいサブエージェントが、生成器を見ずに、生成器を含まない正解の世界の書き出しだけを入力にして新しい書き手を作る（ごみ焼却で、Excel・CSV・PDF・写真の形式ごとに 1 様式以上）。束のハッシュ（ファイルごとの SHA-256 をパスの順に並べた一覧の SHA-256）だけを先にコミットする。
  3. タグを worktree に取り出して読む（主線の開発は続けてよい）。結果の記録に読み手のコミットを書き、試験が「タグと同じ `src/`」を確かめる。
  4. 書き手・種・ファイル・結果を同じリポジトリに公開し、ハッシュが一致することを試験で確かめる。
  - 届かなければ、測った値のまま書く。直してよいのは一般の手がかりと一般の質問の形だけで、直したら新しい見ていない様式（`reader-freeze-2`）で測り直す（同じファイルで測り直すと、その様式に合わせた直しになるため）。手がかりを足すのは、性質の違う 2 つ以上のファイルで質問の数が減ると試験で示せたときだけ。
  - 試験の中の人だけの操作（写真の許し、要確認を受ける）は、試験の台本が人の代わりに押し、結果に「試験の台本が押した」と書く。AI のツールには押させない。
  - 読み手を作るサブエージェントがそのフォルダを読まないことは、仕組みでは止めきれない。証拠は時刻の順とハッシュだと README に書く。
- **AI を入れた 1 回**：主線のセッション自身が MCP のクライアントとして見ていない様式を読み、質問への答えは、正解の世界だけを見る別のサブエージェントが返す。質問の数と ②③ をそのまま記録する（自動の通しの試験は伸びしろ）。
- 試験の表（形式 × 様式 × ①〜⑥）は試験の実行から生成する。緑でないものを緑と書かない。

### 2.7 ほかの設備へ広げる

- **し尿処理**（A 群）：公の項目リストと小さな正解の世界だけのパック。`packs/night-soil/` を足すコミットに `src/` の変更が無いことを試験が確かめ（CI は履歴とタグを全部取る。取れなければ失敗にする）、そのコミットそのもので CI が緑だった記録を残す。そのパックで「取り込み → 当てはめ → 星取表」が通る。公の項目リストは、環境省『廃棄物処理施設長寿命化総合計画作成の手引き（し尿処理施設・汚泥再生処理センター編）』（令和 3 年 3 月改訂。https://www.env.go.jp/recycle/waste/3r_network/7_misc/gl-ple_hw.pdf ）の表Ⅱ-4（印刷頁 27、PDF の 35 枚目。列は「設備」と「装置名」）を使う【確認：運営者の別のセッションが 2026-11-03 に照らした。パックに入れるときに、このセッションでも照らす】。全国の表は、同じ調査のし尿処理施設の表（08.xlsx）。処理方式は「汚水処理」と「汚泥処理」の 2 列で、1 つのセルにカンマで複数の値が入る。運営の形を表す列は「ごみ処理事業実施方式」と「運転管理体制」（「運営形態」という列は無い）。稼働中は、休止・廃止・建設中を除いて約 786 施設【確認：同じ別のセッション】。画面に出す数は、パックの段でこのセッションが数え直し、数え方を書いてからにする。画面では札「パックを足しただけ」を出し、ごみ焼却と同じ厚さのふりをしない。
- パックを足しても `src/` が要らないように、全国の表の列の読み方・軸の決め方・単位は `pack.json` に書き、`national/` は `scripts/` が作る。`src/` は `national/` の決まった形だけを読み、パックは `packs/` を並べて読む。
- **設備の地図**：地図にある設備の種類ごとに 1 つ、名前と出どころの候補だけのパック（中身は空、状態は `未確認`、`sharing: "off"`）を置き、【業種】の画面に A〜H の群で並べる（数は `packs/` から数える）。選ぶと「この業種のパックはまだ中身がありません。出どころの候補：…」と出す。原子力は名前だけ載せ、作らない理由を出す。群ではなく設備の種類ごとにしたのは、使う人が選ぶのは群ではなく自分の設備だから。
- **2 段目の当てはめ**：ごみ焼却・し尿処理の 1 段目の全項目に、2 段目の種類を当てる。これで「送風機」の行のように、業種をまたいで同じ行に並ぶ。
- **公の項目リストが無い業種**（産業プラントの多く）は、法令が名指しする設備（高圧ガスの特定設備、ボイラー・クレーン・圧力容器、危険物の施設など）から 1 段目を作る。その作り方を `docs/industries.md` に書く。中身を入れるたびに、その表に「パック・公の項目リストの出典・照らした度合い・正解の世界の厚さ」を書く。薄いパックは薄いと書く。
- 芯の形（段の数が可変の資産の木、作業と資産の多対多、暦と使用量の早い方のきっかけ）が業種に依らないことが、広げられることの土台。README の「次に広げる順」は、地図の A → H の順。

### 2.8 F2 共有：写すもの・数え方・場・検問所

**考え方**：原本から、許した欄だけを、帯とコードに変えて新しい紙に写します。人が検問所で確かめ、合言葉で署名して、場に足します。守りの根っこは何を運ぶかで、運び方には頼りません。束は、いつか誰にでも見られるつもりで作ります。暗号から借りるのは署名と、前の束のハッシュでつなぐ鎖だけです（トークンも合意の仕組みも使いません）。束・塊・輪・検問所・送り状・台帳は仮の名前です。

**写すもの（塊）**：1 つの施設の、1 段目の項目 × 作業の属性ごとに 1 行。値はどれも閉じた一覧の文字列で、数は書きません。

| 欄 | 中身 | 決めたことと理由 |
|---|---|---|
| `class` | 1 段目の項目のコード | 全国の表で数えられるか `universal: true`（出典つき）の分類だけ。どちらでもなければ数えられる上の分類まで上げ、上げ先が無ければ出さない（分からないものは出さない） |
| `work` | 4 つの属性のどれか | 決まらない行は出さない |
| `years` | 作業をした年度の一覧（`FY2016` の形） | 星取表の列になる。日付は出さない |
| `observed` | 回数の帯（N1 / N2 / N3P） | 生の回数を出さない |
| `interval` | 間隔の帯 | N1 の行には出さない。号炉・系統ごとに数えてから中央を取る（交互に整備しても半分にならない）。号炉の番号と数は出さない |
| `manDays`・`days` | 1 回ごとの工数（人・日）と日数の、中央の帯 | まとめ工事の行と、人・日に直せない書き方は出さない（分けない、推測で割らない） |

- **費用の欄は無い。** 帯にもしない。どの場の決まりでも足せない。生の工数・日数・日付は、その PC の原本にだけある。
- **経過年（最初の作業のときの設置からの年の帯、`ageAtWork`）の欄も無い**（2026-11-03 に運営者が決めた）。塊の年度と合わせると設置の年度が 3〜4 年の幅に絞れ、全国の表の使用開始の年と合わせると 844 施設の多くが 5 施設未満に落ちるため（測った数は `docs/sharing.md` §1.4）。輪にも公開の台帳にも出さず、どの場の決まりでも足せない。設置の年は写さなかった数に数える。受ける側は、経過年の欄がある束と、経過年の欄を許す決まりを、輪でも台帳でも理由つきで ✗ にする。帯と束の型の版は `bands-2`。
- 帯の境目はコードの定数で、場の決まりは粗くする向きにだけ変えられる。初めの値は設計の案（間隔 I1〜I16_30、工数 W1_9〜W1000P、日数 D1_3〜D121P、処理能力は 50・100・200・400 t/日で区切る）。**11-05 の夜に工場の正解の世界で k と見え方を確かめてから決め、理由と一緒に `docs/sharing.md` に書く。束を作るのはそのあと**（帯は束の型と台帳の検証の版に入るので、あとで変えると束も PR も作り直しになるため）。
- `UPGRADE` の塊は基幹改良の実施を明かし、全国の表では数えられないので、輪では k ≥ 5 のときだけ出し、公開の台帳には出さない。記録に ID を付けず、コード順に並べる。
- 写すのは、人が画面で受けた当てはめだけ。案のままの記録は「当てはめを人が受けていない」に数える。写さなかった行は、理由ごとに数えて検問所に出す。
- **束**：1 施設を 1 回送ると 1 束。中身は見え方（`profile`）・塊の並び・送った月・送る側で数えた値。施設をまたいで混ぜない。束の本文には行き先（輪の ID か台帳の ID）を入れて署名し、ほかの行き先の束は ✗ にする。

**見え方と紛れる数 k**：

- 見え方の軸とその順はパックが決める。ごみ焼却は、主要＝炉の型・処理能力の帯、次＝蒸気タービン・集じん・灰処理、絞り込み＝基幹改良・運営の形。ほかに集団（全国の表に載る `NATIONAL`／載らない `OUTSIDE`）と段（0〜3。3 は業種だけ）。使用開始の年は入れない（年を足すと、多くの施設が 5 施設未満に落ちるため）。
- k は、見え方に、塊から推せる属性（発電の有無・灰の処理の方式など、全国の表に列があるもの）も足して数える。段の順はコードに 1 本だけ持つ：後ろの軸から外し（運営の形 → 灰処理 → 蒸気タービン）、同じ段で、外した軸を推せる分類も上へまとめる → 処理能力の帯を粗くする → 下の段へ。最初に k ≥ 5 になった段で止め、段 3 でも届かなければ送らない。人は粗くすることだけができる。
- 全国の表に列が無い軸（集じん・基幹改良の実施）は、公開の台帳に出さない。輪では、確認済みの仲間の最新の束（鍵ごとに 1 つ、自分は数えない）で数えて k ≥ 5 のときだけ出す。
- 数える集団：`NATIONAL` はパックの `national/`（そのハッシュを `circle.json` と `ledger.json` に固定し、送る側・受ける側・Actions で同じ表を使う）。`OUTSIDE` と表の無い業種は、輪の中の確認済みの仲間の最新の束。段 3 は公的な統計の総数（出典つき）。
- 下限はコードに固定（送る側 k ≥ 5、受ける側の見せる下限 ≥ 3）。受ける側で軸を足して 5 未満になったら「この条件では 5 施設に届かない」と出す。統計の行（n は自分を除いた施設数、塊ごと、周期・工数・日数のそれぞれ）は、n が 0〜2 なら「x」、3〜4 なら幅の帯と n、5 以上なら中央の帯・四分位の帯・n。集団を混ぜて集計しない。公開の台帳は `NATIONAL` だけを受ける。`sharing: "off"` のパックは共有を切る。

**数え直しと署名**：

- 送る側と受ける側が同じ関数で数え直す。引数で緩められず、切り替えも持たない。対象は束のファイル全体のすべての文字列（`members`・`circle` も同じ）。数えるのは、形の外れ（`{body,sig}` の JCS と完全に同じバイト列か。キーの重複・BOM・余分な空白・型に合わない値・知らないキー）、自由記述（公開語彙に無い文字列。ASCII 以外の文字も数える）、金額の形、正確な日付（年月日・和暦。`years` の `FY` の形と送った月 `month` は数えない）、k、署名と鎖（署名・`prev`・`seq` の抜け、覚えた最大の `seq` より小さいか）。
- 固有名詞は、送る側だけの別の関数が数える。照らす語は、その PC だけの語の一覧（計画と取り込みの施設名・業者・実施者から自動で作る。利用者は足せるが、用意しなくても送れる）と、原本の全セルの文字列（日本語 2 文字以上・英数 3 文字以上。数だけと語彙のコードは除く。送るたびにメモリで作り、残さない）。照らす相手は、束のバイト列（NFKC）・ファイル名・輪のフォルダのパス。評価の問題の文（F3）を照らす関数は、また別の名前にする（束の関数を使い回さない）。
- 署名のコードは、形の外れ・自由記述・金額・正確な日付・固有名詞が 0、k ≥ 5、合言葉が合う、がそろったときだけ署名する。プレビューと送る処理は同じ関数で同じバイト列を作り、ハッシュが違えば送らない。
- 正規化は RFC 8785（JCS）を自作し、正規化した body の SHA-256 に Ed25519（Node の crypto）で署名する。秘密鍵は、合言葉から scrypt で作った鍵で包み、状態フォルダに置く（OS の鍵の保管は未実装と README に書く）。束の鍵は 2026-11-04 に施設のものに変えた（§2.19：計画のフォルダに包まずに置く）。鍵は輪ごとに作り、同じ施設を 2 つの輪に送るときは中身が同じなのでつながることを画面で知らせる。受け手は仲間ごとに見た最大の `seq` を覚え、減ったら「前に見た束が消えています」と出す。仲間の鍵は最初に見たときに信じ、指紋 16 文字（4 文字 × 4 組）を電話で読み合わせたら「確認済み」。それまでは k に数えない。ブラウザでも WebCrypto の Ed25519 で検証し直す（Chrome 156・Edge 156 で動くかを、最初の日の試験のページで確かめる【未確認】）。

**場 1　輪**（保全子会社の自社の輪、拠点どうし、勉強会など）：

```
<輪のフォルダ>/<輪ID>/
  circle.json                                  輪の決まり（作った人が署名。輪 ID はそのハッシュから）
  members/<鍵ID>.json                          公開鍵と状態だけ（本人が署名。表示名は置かない）
  bundles/<鍵ID>/<連番>-<ハッシュ先頭16>.json    束（足すだけ）
```

- 各人は自分の `bundles/<鍵ID>/` にだけ足す。消さない・直さない。読む側は毎回ファイルから計算する（これが DB の代わり）。
- 書くときは、一時の名前で書き、更新時刻をその月の 1 日 0 時にそろえてから rename する（Windows で置き換えが断られたら数回だけ置き直し、だめなら「結果不明」と出す）。読めない・途中で切れた束は「届きかけ」として ✗ と分ける。橋渡しは、正しい束の形のファイルしか輪のパスに書かない。
- 表示名は輪に置かない。受け手が自分の PC で指紋に呼び名を付け、呼び名は AI に渡さない。人は輪 ID の文字を打たない。
- `circle.json` にできるのは厳しくすることだけ（欄はコードの許可リストの中から選ぶ、帯は粗くする向きだけ、下限は下げられない、公開語彙と `national/` の版とハッシュを固定する）。各 PC は人が受け入れた決まりのハッシュを覚え、変わったら送る前に差を出し（「決まりが変わりました：緩くなった 1、厳しくなった 0」）、人が画面で受け入れるまで送らない。
- 橋渡しは自分の `bundles/<鍵ID>/` を見張り、持ち出し簿に無いハッシュのファイルが現れたら赤で知らせる（「あなたの名前の場所に、検問所を通っていないファイルがあります」）。受け手は束の形をしていないファイルも数えて出す。
- P2P はアプリが持たない（使うなら Syncthing などに任せる）。

**場 2　公開の台帳**（別のリポジトリ `mushitaro/moyai-ledger`。§7）：

```
ledger/ledger.json      台帳の決まり（管理者が署名。circle.json と同じ形で、厳しくする向きだけ）
ledger/TERMS.md         利用条件：共有する値は塊の周期・工数・日数の帯だけ。費用は共有しない
ledger/bundles/<鍵ID>/<連番>-<ハッシュ先頭16>.json
site/                   GitHub Pages の静的なサイト（ビルドのときに束から集計して描く）
.github/workflows/      PR の検証、マージのあとの集計と公開
```

- 登録は、人が SHARE（検問所）を通して合言葉で署名した束を、MOYAI が PR で出す（運営者の決定、2026-11-04：「MOYAI が出す」。人が GitHub で出す道と比べたうえで）。PR を出すのは、人が画面でボタンを押し、合言葉で束に署名したときだけ。PR を出す処理は AI のツールにしない（決まり 1 は変わらない。送るのは人で、MOYAI はその道具）。MOYAI は利用者の GitHub のアカウントで台帳のリポジトリをフォークし、束のファイル 1 つを足す枝を作って PR を出す。CLI の `ledger submit` は、試験と人の予備の道として残す。
- 検証は `pull_request_target` で、既定のブランチにある定義を走らせる（守り方は下）。検証の中身はアプリと同じ関数（形・署名・鎖・粒度・禁止語・数え直し・k）で、理由を PR に出す。必須のチェックにし、管理者も越えられない設定にする。マージを決めるのは管理者（人）。押すのは、管理者か、管理者がその都度チャットで指示した作る側のセッション（2026-11-04 の運営者の決定。§7）。
- マージのたびに、束から似た施設の匿名の星取表と統計の行を描き、Pages に出す（アプリと同じ集計の関数）。束のファイルは誰でも開ける。審査員は台帳を clone して `node dist/cli.js verify ledger <台帳の場所>` でも同じ検証を回せる。
- 会期中は架空の施設だけ（10 前後。x・幅の帯・中央の帯がどれも出る数）。架空の 10 施設は 1 つの PR にまとめ、運営者のマージは 1 回にする。k < 5 の束・費用の欄がある束・施設名が入った束の PR も出し、Actions が理由つきで ✗ にした記録を残す。これらの PR は作る側のセッションが架空の束で出したものなので、PR の本文と README にそう書く。施設名を出すかは運営者が決める（会期中は匿名の札）。
- PR を出した GitHub アカウントは誰にでも見える。検問所で必ず知らせ、台帳専用のアカウントを勧める。
- GitHub を使わない職員のための受付（同じ検証をして PR を作るだけ。DB なし）は、会期の後の構想として README に書く。

**台帳の守り方**（運営者の別のセッションが 2026-11-03 に照らした事実をもとに決めた）：

- GitHub は 2026-12-02 から、公開リポジトリの `pull_request_target` を既定で止める。その前の試しの停止が 2026-11-09 と 11-16 の 16:00〜18:00 UTC（日本時間 11-10 と 11-17 の 1:00〜3:00。決勝の 11-10 13:00 には掛からない）にある（https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2 ）。台帳のリポジトリを作ったらすぐ、Settings → Actions → Policies で event policy を作り、`pull_request_target` を検証のワークフローのファイルにだけ許す。`pull_request` は許さない（許すのは push・pull_request_target・workflow_dispatch だけ。偽のチェックを防ぐため）。効いていることを Policy insights で確かめ、日誌に残す。
- 権限：ワークフローの先頭に `permissions: {}`。検証のジョブは `contents: read` だけで、secrets もトークンも使わない。PR に結果を書くジョブは `pull-requests: write` だけで、検証とは別のジョブにする。pages・id-token・environment は付けない。既定のトークンは read にし、「Actions に PR を作らせる」はオフのまま。
- 中身の読み方：checkout は ref を指定せず（main を取る）、`persist-credentials: false`。PR の head は `git fetch --no-tags origin <head の SHA>` でオブジェクトだけを取り、checkout しない。変更の一覧は `git diff --raw -z --no-renames --no-ext-diff --no-textconv <base>...<head>`、中身は `git cat-file blob <head>:<path>` で読む。head の側で npm install・ビルド・スクリプトを走らせない。
- 許すもの：状態が追加（A）で mode が 100644 の、`ledger/bundles/<鍵ID>/` の下のファイルだけ。削除・変更・改名・型の変更（D・M・R・T）、symlink（120000）、submodule（160000）、大文字小文字や Unicode の正規化だけが違うパス、`.github/` に触れるものは ✗。鍵 ID と出した人の結びつきは、束の署名をその鍵の公開鍵で確かめて決め、GitHub のログイン名には頼らない。
- 注入を防ぐ：PR のタイトル・ブランチ名・ファイル名を `run:` に直接埋め込まない（env で渡して引用する。ファイル名は NUL 区切りで扱う）。`GITHUB_ENV`・`GITHUB_OUTPUT` に PR から来た値を書かない。PR への書き込みは本文をファイルで渡し、ファイル名はコードの枠に入れる。
- 必須のチェック：必須にするジョブには if も paths の絞り込みも付けない。名前は一意（`ledger-validate`）にし、出どころは GitHub Actions に指定する。同じ PR の古い run は concurrency で止める。入力に上限（ファイルの数・大きさ・深さ）と `timeout-minutes` を付ける。MOYAI はタグではなく commit の SHA で固定し、`npm ci --ignore-scripts` で入れる。JSON は `__proto__` と知らないキーを拒む。
- main の守り：ruleset で PR を必須（承認は 0）、必須のチェック、force push と削除の禁止、bypass の一覧は空にする。オーナーは設定そのものを外せるので、これは運用の決まりだと README に書く。
- Action はフルの SHA と版のコメントで固定する（候補：`actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`、`actions/upload-pages-artifact@fc324d3547104276b827a68afc52ff2a11cc49c9 # v5.0.0`、`actions/deploy-pages@368f82528645a54fb793d4d04e342629a3f51346 # v5.0.1`、`actions/configure-pages@45bfe0192ca1faeb007ade9deae92b16b8254a0d # v6.0.0`、`actions/github-script@3a2844b7e9c422d3c10d287c895573f7108da1b3 # v9.0.0`。使う前に `git ls-remote` で照らす）。SHA での固定を求める設定をオンにする。
- Pages：`on: push`（main、`ledger/**`）と `workflow_dispatch`。build のジョブは `contents: read`、deploy のジョブだけ `pages: write` と `id-token: write`（environment は github-pages）。main を取り直して全部の束を検証し直し、確かめたデータから HTML を作る（生のファイルを写さない。symlink は拒む。HTML はエスケープし、CSP を付ける）。workflow_run や、ほかの run の artifact は使わない。検証のワークフローでは cache を書かない。

**受け取りと 3 つの立場**：

- 全員の `bundles/` を読み、束ごとに形・署名・ハッシュ・鎖・決まりの版・数え直しを確かめ、仲間ごとに ✓ か理由つきの ✗（形の外れ／署名 ✗／抜けあり／古い決まり／未確認の仲間／届きかけ）を出す。✓ の束だけを足し合わせる。
- 自分の星取表の下に、似た施設を匿名の札（類似施設 A・B…）で並べる。札は受け手の PC が鍵の指紋ごとに付け、AI には札だけを渡す。統計の行とパックの基準は、別の色と見出しにする（§2.2）。AI は周期の案を置けるが（根拠「類似施設 n、中央の帯」）、確定は人。参考は「なぜ違うか」を考える入口で、正解ではない。
- 立場：市町村（自分の施設の計画 ↔ 公開の台帳の、見え方が似た施設）、保全子会社（自社の輪の納入プラント ↔ 公開の台帳）、O&M 事業者（入札の対象と同じ見え方 ↔ 公開の台帳と自社の輪）。画面は 1 つで、並べる集まりだけが変わる。n と値は場のファイルから計算して描き、手で書かない。デモの輪は 7 拠点（自分を除いて n が 6 まで出る）。`node dist/cli.js verify demo-ring` で、デモの輪の全員の束を同じ関数で確かめられる。

**検問所の画面**（運営者の画面の約束どおりに作る）：

### 2.9 確定と書き出し

- **確定は人だけ。** 星取表の［確定する…］で、差分の要約と一言の理由（空は通さない）を出し、人が確かめて確定する。作者が「AI」の決定と、AI が会話から写した人の答え（作者「AI（チャットでの人の答え）」）は「人が受けていない決定」の一覧に出し、人が画面で受けるまで確定できない（受けるときにも一言の理由）。
- 変更には必ず作者と根拠を付ける。作者の種類は「人」「AI」「AI（チャットでの人の答え）」「AI（読み取り）」「決まり（コード）」で、画面で人が答えたものだけを「人」とする。根拠は 1 文字以上を型で求める。人・拠点・クライアントの ID も残す。変更は元の値を書き換えずに重ね、まとめて取り消せる。
- 確定した計画は `MOYAI/plans/<計画ID>/` に、計画のファイル（検査の結果とレビューも含む）、前の版（足すだけ。戻すのは前の版を指す記録を足すこと）、差分レポート、書き出しを置く。計画の ID と表示の名前を分ける。
- **差分レポート**（Excel）：機器名・作業名・年度・印の前後・誰が・なぜ。版どうしの差は画面でも見せる。
- **書き出し**（人が見る様式の Excel）：入れ子、縦の結合、行のグループ（アウトライン）、小計の行、A3 横の印刷設定、ウィンドウ枠の固定、凡例、【架空】。平らな表にはしない。
- 置き場所の既定は OS の Documents の下の `MOYAI/`。起動のたびに、Documents が OneDrive などの同期フォルダの下にあるかを調べ、下にあれば画面に出して置き場所を選んでもらう（調べ方は §2.12）。**この PC の Documents は OneDrive の下にある**【確認：`C:\Users\<利用者>\OneDrive\ドキュメント`、2026-11-03】ので、実機でこの道を必ず通る。
- タブを閉じる前に、確定前の変更があれば知らせる。ダイアログは変更を捨てる前に確かめ、保存に失敗しても閉じない。

### 2.10 F3 Skill の採点

- 呼び名は「Skill の調整」「Skill の採点」。重みは変えない（Claude API では、利用者が重みを変える学習はできない【確認：platform.claude.com の用語集。設計書を作ったセッションが 2026-11-02 に照らした】）。
- 輪：確定した計画・差分・決定（人の判断）＋パックの規則 → 評価の問題（学習用／試験用。期間か拠点で分ける）→ Skill の新しい版 → 前と後を同じ条件で走らせる（モデル・effort・system・max_tokens・Skill の版を固定、1 問 3 回）→ 採点（コードが先、人は変わった問題と割れた問題だけ）→ 表（点・問題ごとの前後・外へ出た文字・費用）→ 人が昇格（pins に 1 行足す。戻すのは前の版を指す行を足すだけ）。
- **新しい版は私（作る側のセッション）が案として書き、作者を AI と出す。保存と昇格は運営者が画面でする**（運営者の決定、§7）。
- **本線（約 6 時間）**：`moyai eval` の CLI、問題の形と分け方、規則の生成器（工場の正解の世界を使い回す。規則 10 前後 × 10 問。候補：周期の欄が空なら推測しない、番号の違う機器を名前でまとめない、出典はパックの一覧の中から、年度の始まりはパックどおり、記録に無いことは「記録に無い」と言う、和暦の年度、範囲のタグ、凡例に無い記号、合計の行を作業にしない、単位の違う工数）、Messages API で 3 回走らせる仕組み（条件の固定、費用の記録）、コードの採点 6 種（JSON として読めるか／周期を推測で埋めていないか／番号の違う機器を名前でまとめていないか／出典がパックの一覧の中にあるか／年度の始まりがパックどおりか／記録に無いことを「記録に無い」と言えたか）、`report.json` から作る静的な表。
- 温度・top_p・top_k は渡さない。effort は毎回明示する。記録（`results.jsonl` など）には、`config/models.json` の項目名とそのハッシュ、応答のモデルが頼んだものと同じだったか、別のモデルへの切り替えがあったかだけを書き、識別子の文字は書かない。切り替えた回、拒否で止まった回、max_tokens で止まった回は集計から外し、その数を出す。
- 自動の見立て（決めるのは人）：コードの採点で落ちる問題が増えた → 退行あり。差が揺れの幅に収まる → 差なし。ほか → 承認待ち。揺れの幅は、前の版を 3 回走らせたときの合格率の最大と最小の差とし、1 か所の定数で決める。小さな差を「改善」と書かない。
- 評価で Claude に送る文字は、走らせる前に全文を出し、固有名詞の当たりが 0 であることを数える（束とは別の関数）。本文を正規化してハッシュを取り、近い重複を除く。試験用の問題のハッシュを `suite.json` に書き、調整する側の入力に入っていれば走らせる前に止める。施設の値はコードと帯に置き換え、デモは架空のデータだけ。施設ごとの Skill はアップロードしない。
- 費用は 1 回ごとに `manifest.json` と表に書き、運営者の枠（F3 の評価に $60。§7 の 2026-11-03 の決定）の中で使う。走らせる前に見込みを出す。
- 置き場所：Skill の版は `MOYAI/skills/<名前>/versions/<UTC時刻>_<メンバーID>_<sha8>.md`（足すだけ）、昇格と戻しは `MOYAI/catalog/pins.jsonl`（足すだけ、前の行のハッシュを持つ）、評価は `eval/<suite>/`（suite.json、cases/{train,test}.jsonl）と `eval/runs/<runId>/`（manifest.json・results.jsonl・report.json）。
- 伸びしろ（本線のあと、この順）：審査の画面（昇格のボタンは差なし・退行ありでは押せず、理由を横に出し、押すと承認する人の一言を求める）、pins と戻しと拒む試験、運営者の判断の問題（20 件。入れると決めたときだけ頼む）、LLM の採点役（文章の質だけ）、Message Batches、Agent Skills API。

### 2.11 F4 手元のモデル（構想）

- **必ず作る L0**：構想の図と、「設定のモデルの一覧に『手元のモデル』の行が 1 つ増える」画面の絵。どちらも静的な HTML で、欄の名前だけを描き、値の所は「L1 で測る」と書く（無いモデルの数を描かない）。「構想」の札を付ける。図には新しいリポジトリにある部品だけを描き、ほかには「構想」の札。本物の設定の画面には置かない。
- 構想の中身：事実は道具（MOYAI のツール）で引き、モデルに覚えさせない。伸ばすのは、作業記録の構造化、機器名から分類コード、規則違反の見つけ方、「記録に無い」と言う癖。データは現場から出ない（学習も推論も手元）。F3 と同じ問題・採点・表で、A 手元の素のモデル／B 素のモデル＋Skill／C 手元で調整したモデル＋Skill を比べ、C が B を上回らなければ「価値は短いプロンプト・オフライン・小さい機械の側」と表に書く。切り替えは人が設定で行い、確定・送る・昇格はどのモデルにもツールとして渡さない。
- L1（合成データだけの小さな LoRA を llama-server で比べる）は、本線と F3 の伸びしろが終わり、凍結までに余裕があるときだけ。学習データはコードの語彙だけで作った文に限り、LLM が書いた文字列を入れない（Claude の出力を正解にしない）。

### 2.12 全体の形と守り

```
AI クライアント（Claude Code / Claude Desktop。写真もここで読む）
  │ 標準入出力の MCP（moyai mcp：つなぐだけの中継）
  ▼
橋渡し（moyai start：1 プロセス、127.0.0.1 の 1 ポート）
  ├ HTTP：静的ファイル・単回のアップロード・人だけの操作・輪のフォルダ（すべて許可の一覧）
  ├ WebSocket：タブとの往復（Origin の一致が必須。タブは 1 つだけ）
  ├ 署名のコード（条件と合言葉がそろったときだけ）
  └ 外へ出た台帳（AI への結果の件数・大きさ・種類と会話の合計。中身は残さない）
  ▼
作業画面（Chrome / Edge のタブ 1 つ。作業中の正本はメモリだけ）
  ├ 取り込み・検査・写し取り（純粋な TS。UI もネットも持たない）
  └ React（Mantine＋AG Grid）
```

- 中継は、橋渡しが起きていなければ「先に `moyai start` を」と返す。中継と橋渡しの間は、状態フォルダの鍵ファイル（利用者だけが読める）で確かめる。同じ利用者のプロセスには読めることを `docs/security.md` に書く。中継の 1 つの接続を「会話」と数える（行を読む上限と、Skill の文を送ったかはこの単位）。
- 導入：`node dist/cli.js setup` は、Claude Desktop の設定に moyai の 1 行だけを足す（ほかのサーバーは消さない。書く前に何を変えるかを出し、端末で「はい」をもらう）。`node dist/cli.js start` で橋渡しを起こす。Claude Code にはリポジトリの `.mcp.json` でつなぐ。ビルドした JS を動かす。

決めた値（この PC で測ってから直す。値は実機の速さで決める）：

| 項目 | 値 | 理由 |
|---|---|---|
| ポート | 既定 43110。使われていれば起動を止め、理由と `--port` を出す | 黙って別のポートへ移ると、Origin の照合・中継の行き先・撮影の手順が狂うため |
| タブ | 1 つだけ。2 つ目は断り、理由を出す | 作業中の正本を 1 か所にするため |
| AI のツール → タブ（読む） | 20 秒。1 回だけ送り直す | 読み取りは送り直しても害が無い |
| AI のツール → タブ（案を置く） | 30 秒。送り直さず「結果不明」と返し、画面にも出す | 書き込みは自動で送り直さない |
| 計画を作る | `intake_compose` は 20 秒以内に「作り始めた」印を返し、結果は次の `intake_survey` で返す | AI クライアントの側の待ちの上限（60 秒ほど）を越えて、作れたのに誤りと見える形を避けるため |
| 写真を AI に渡す | 1 回に 1 枚。表の部分を切り抜き、長辺 1,568〜2,000px、JPEG で約 100KB 以下にする。細かい表は分けて送る | Claude Code は 2.1.128 以上で結果の画像を読み、画像 1 枚をおよそ 1,600 トークンとして結果の上限（MAX_MCP_OUTPUT_TOKENS、既定 25,000）に数え、画像の大きさの上限は既定で 2,000px【確認：運営者の別のセッション】。1 枚ずつ人の許しと結ぶため |
| タブの生存確認 | 15 秒ごと。45 秒で切れたと見なし、ツールは「作業画面が開いていません」と返す | 黙って待たせない |
| 行を読む上限 | 1 回 200 行、会話で 2,000 行 | 1 回の上限は繰り返せば越えられるので、会話の合計に上限を置き、外へ出た台帳に合計を出す |
| アップロード | 1 ファイル 64 MB まで | 写真と PDF の束で足り、メモリを守れる |
| 状態フォルダ | Windows は `%LOCALAPPDATA%\MOYAI\state\`（同期されない場所。利用者だけが読めるのは、このフォルダの既定の権限に頼る）。macOS・Linux は利用者だけが読めるフォルダ | 人の秘密鍵・GitHub のトークン・対応表を、同期フォルダから外すため（施設の署名鍵と持ち出し簿は、2026-11-04 から計画のフォルダ。§2.19） |

- **タブの秘密**：ページの中で作り、最初の WebSocket の握手で橋渡しに登録する。HTML にも、どの GET にも入れない。
- **1 回きりの印**：橋渡しが作る。確かめのダイアログを開いたときに WebSocket で渡し、その操作と中身のハッシュに結ぶ。120 秒で切れ、1 回使うと消える。
- **人だけの経路**（どれも許可の一覧に載せ、タブの秘密と 1 回きりの印を求める。一覧に無いものは拒む。拒む試験は消さない）：計画の確定、AI の決定を受ける、対応表（当てはめ）の保存、写真を AI クライアントに渡す許し、束を送る（署名と書き込み）、輪の決まり・仲間・鍵・設定、決まりの変更の受け入れ、辞書の保存、Skill の版の保存、Skill の昇格。
- **網の外側**：127.0.0.1 だけで待ち受け、Host・Origin・Sec-Fetch-Site を確かめ、DNS リバインディングを断る。これは Web ページ対策で、同じ PC のプロセスは防がない（curl も Node も Origin を偽れる）。README と動画で言うのは「AI のツールに無い／素の curl は拒む／同じ利用者のプロセスは止めきれない」まで。
- **ツールだけを持つ AI**（Claude Desktop など）からは、型と許可の一覧で人だけの操作を外す。**シェルを持つ AI**（Claude Code など）には、リポジトリの `.claude/settings.json` の deny と、PreToolUse のフック（`scripts/guard-hook`）の二重で外す：
  - deny：`WebFetch(domain:mxstage.tsunagi.app)`、この PC に入っている前の製品の MCP のサーバー単位の deny、127.0.0.1 への HTTP、状態フォルダの読み取り（Windows のパスの書き方は最初の日に確かめ、確かめるまではフックで止める）。
  - フック（matcher は `Bash|PowerShell|Read|Grep|Glob|Write|Edit|WebFetch`）：127.0.0.1・localhost・[::1] への curl・wget・`Invoke-WebRequest`・`iwr`・`irm`、`$env:LOCALAPPDATA` を含む状態フォルダの読み取り、輪のフォルダへの書き込み（輪のフォルダは毎回、状態の設定から読む）、github.com/mxstage と github.com/woodygaragelab/hoshutaro の取得と clone、人だけの CLI。判定の関数を、止める呼び出しと通す呼び出しの両方で試験する。
  - 人だけの CLI（`ledger submit`、鍵を作る、`setup` の確かめ）は、標準入力が端末でなければ断る。
  - 悪意のある同じ利用者のプロセスは止めきれないと書く。
- この PC の Claude Code には前の製品の MCP と Skill が入っている。MCP のツールはこのリポジトリで deny にし、Skill は呼ばない（Skill を止める設定があるかは最初の日に確かめる。このセッションでは、どちらも呼んでいない）。収録はクラウドの新しい環境で行い、MCP と Skill の一覧が MOYAI だけであることを画面で確かめてから撮る。この PC で撮るときは、新しい設定のフォルダで Claude Code を起こし、同じことを確かめる。
- **API キー**は環境変数（手元）と Actions の secret（監査）だけに置く。製品の中で使うのは `moyai eval`（F3）だけ。作る側では、監査のエージェントと開発のエージェント（§3）が使う。チャットでもツールでも受け取らない。
- **記録**：作業データ・キー・行の値をログにも console にも出さない。標準出力は MCP だけに使う。製品のクラウドもテレメトリも無く、ほかの通信は既定でオフ。
- **通信の例外は公開の台帳への PR だけ**（運営者の決定、2026-11-04）：行き先は api.github.com と github.com だけ。PR を出すのは人がボタンを押したときだけ、出した束の行方（PR の状態）を読むのは SHARE を開いたときだけ。GitHub へのつなぎ方は OAuth のデバイスフロー（人が github.com でコードを入れる）で、scope は public_repo だけ。トークンは状態フォルダに置き、画面にもログにも AI にも出さない（合言葉では包まない。運営者「パスワードは絶対いやです」、§2.19）。設定に「GitHub との接続を切る」を置く。

- **AI に渡る範囲**は、ツール定義の 1 か所（`src/shared/`）で決め、`docs/security.md` と画面の［AI に渡るもの］はそこから生成する。`docs/security.md` と稟議に付ける表には、保証できないことをそのまま書く：① 1 回の上限は繰り返し呼べば越えられる（だから会話の合計に上限を置き、台帳に合計を出す） ② チャットに Excel を添付すれば、ファイル全体が AI の提供者に渡る ③ ファイルを読める AI は、確定した計画のファイルを直接読める ④ Documents が同期フォルダなら、確定した計画は会社のクラウドに上がる（だから最初に調べて知らせる） ⑤「外へは送らない」はアプリの通信の話で、データの行き先の保証ではない ⑥ 写真とスキャンの読み取りでは、人が許したその画像が AI の提供者に渡る ⑦ 画面を操作できる AI の道具（ブラウザやデスクトップの操作）は、人だけのボタンを押せる。
- 伸びしろ：送る・昇格に、人がその場にいる証（WebAuthn の利用者確認＝Windows Hello）を求める。

### 2.17 Skill の 3 段と、読み方（運営者の設計。2026-11-04）

見ていない様式の試験（heldout-1〜3）で、読み手のコードを足すだけでは、新しい様式で毎回どこかで詰まると分かった。製品の答えは、詰まったら利用者と Claude が会話で決め、その読み方を Skill として残し、社内で共有することにする。

Skill は 3 段：

| 段 | 中身 | 編集 |
|---|---|---|
| 1 基本操作 | Claude チャット・利用者・MOYAI をつなぎ、利用者の求めに対して Claude が MOYAI の操作をすべて実行できるようにする。MCP とセット。取り込みを詰めきれないときの手順（下）もここに置く | できない（標準） |
| 2 業界の標準パック | 設備の種類ごと。基準書・国や協会の指針・法令、機器の構成、機器台帳の作り方、階層の考え方、代表的な保全作業、履歴に基づく計画の作り方、共有台帳の作り方と参照の仕方など | できない（標準） |
| 3 独自の読み方 | 設備・会社・担当者ごと。1・2 段を補うか置き換える（置き換えは、規則に置き換えると書いたときだけ）。Claude が会話から作り、利用者が手で編集してもよい | できる |

- **置き場所**：版と署名を置く保管先（設定で 1 つ）の下だけ（運営者の決定：星取表と Skill の保管場所は同じ）。
  - 置いた場所が範囲を決める：`<保管先>/skills/会社/<名前>/`・`<保管先>/skills/担当/<呼び名>/<名前>/`・`<保管先>/<施設>/skills/<名前>/`。
  - 当てる順は 施設 → 担当 → 会社 → 2 段 → 1 段。
- **中身**：`SKILL.md`（人と Claude が読む文）と `rules.json`（読み手が当てる規則。形は moyai.reading/0）。中身のハッシュが版で、前の版は消さない。
- **規則**：会期中は決まった形の規則だけ（任意のコードは、承認する人が読めないので会期の後）。
  - 種類：見出しの行・列の役目・日付の書き方・工数の単位・行の役割・同じ機器（辞書）・印の意味・同じ様式の同じ質問への決まった答え。
  - どの資料に効くかは、見出しの文字の並び（様式）で決める。
  - 画面では 1 規則 1 行の人の言葉にする（体言止めか「〜として読む」。名前は「」で囲む）。
  - 規則で決まったものは質問にしない。作者は「規則（<名前> 版 xxxx）」。
- **詰めきれないときの手順**（1 段目）：
  1. 開いたままの質問と読み違いの見本の行を見せる。
  2. 何がどうなっているかを会話で聞く。
  3. 規則にして作業中の版に下書きで置き（`reading_rules_propose`）、読み直した結果を見せる。
  4. 利用者が良ければ、保管先に未承認の読み方として書く（`reading_skill_register`）。
- **承認**：星取表と一緒に、版の署名 1 回で承認する（MERGE の「読み方」のタブと、横の板の「使った読み方」）。
  - 置いただけの読み方は「未承認」で、作った人の下書きの版の中でだけ効く。
  - その読み方を使った版が署名を受けたとき承認済みになり、ほかの人の MOYAI でも効く。ファイルを置いただけでは、ほかの人の読み方は変わらない。
  - 規則を変えて前の版で承認済みのセルが変わるときは、星取表の「前の版から変わった」朱の印を、そのセルに乗せる。
- **決まり 1 の例外**（運営者の決定）：確定・送る・昇格・保存は人だけ、の例外は 2 つ。
  1. 引き渡しのメールを Claude が送る。
  2. 未承認の読み方の下書きを、Claude が保管先に書く。
  - 承認は、どちらも人の署名のまま。

#### 2.18.2 版と署名（承認の土台）

決まり：確定・承認・差し戻しは、人が合言葉で開く自分の鍵の署名でする。AI に鍵も合言葉も渡らない。

- **署名する文**：`{ schema, planId, version, contentHash, role, by, key, at, reason }` の JCS。
  - contentHash は、版の記録（計画・受けた決定・使った読み方・親）の JCS の SHA-256。画面の「4 文字 × 2 組を 4 つ」はこれ。
  - role は `confirm`（自分で確定）・`edit`（編集を頼んで渡す）・`approve`（承認）・`return`（差し戻し。理由は必須）・`revert`（前の版に戻す）。役目と理由も署名の中に入れ、書き換えに気づけるようにする。
- **置き方**：版の記録は今のまま 1 度だけ書く（`versions/<版>.json`、wx）。署名は 1 つずつ別のファイルにする（`signatures/<版>-<role>-<鍵ID>.json`、wx）。同じ版にあとから承認が足されても、版のファイルを書き直さない。
- **鎖**：次の版の記録は、親の版の contentHash と、親の版の署名のファイルのハッシュの列を持つ。承認や差し戻しの署名を消すと、鎖で気づける。派生（derivedFrom）は、ほかの施設の版の planId・版・contentHash。
- **前の形の版**：署名の無い前の形の版（moyai.version/0）は「署名の無い版」として読むだけにし、承認には数えない。
- **人の鍵**：1 人の呼び名に鍵を 1 つ以上（PC を替えたとき・鍵を失ったときに足す。古い鍵は消さない）。Ed25519。秘密鍵は状態フォルダ（同期されない場所）に置く（2026-11-04 に合言葉で包むのをやめた。§2.19）。公開鍵と呼び名は、保管先の `people/<鍵ID>.json` に置く。輪の鍵（束に署名する。輪ごと）とは別にする。輪の鍵は輪の中で誰の束かを分からせるもので、施設の版の承認とは役目が違うため。
- **鍵を信じる**（輪と同じ型。§2.8）：保管先の `people/` は、そこに書ける人なら誰でも置けるので、信じる元にしない。各 PC は、確かめた鍵（呼び名 → 指紋）を自分の状態フォルダに覚える。指紋 16 文字を読み合わせたら「確認済み」。それまでの署名には「! 未確認」と出し、その署名では読み方を承認しない。覚えた呼び名の鍵が替わったら知らせる。
- **確かめ**：版を開くたびに、署名の文・署名・鎖・鍵を確かめる。合わなければ版を開かず、何が合わないか（ハッシュ・署名・場所）を 2 文で出す（`docs/screens.md` 4 の 8）。
- **止め札**（署名の前に、どれか 1 つでもあれば押せない。理由を下の帯に出す）：決まっていない所、受けていない決定（MERGE の決定のシート）、保管先に作業を始めた版より新しい版がある（4 の 6）、橋渡しとつながっていない（4 の 5）。
- **編集の番**：保管先の `plans/<計画ID>/turn.json`（いま誰か・どの版から・時刻）。渡す・差し戻すで替わる。
- **承認の範囲は、渡すとメールまで作る**（運営者の決定、2026-11-04）：自分で確定する・編集を頼んで渡す・承認を頼む・承認して署名する・理由を添えて差し戻す、と編集の番と、渡すメール（`docs/screens.md` 3.4）。メールは、MOYAI が署名して版の場所とハッシュを書いた文を用意し、Claude が利用者の連携したメールから送る（決まり 1 の例外の 1 つめ）。MOYAI 自身はメールを送らない。
- **承認と読み方**：署名のダイアログに「この署名で承認する読み方」（名前・範囲・規則の数・下書きか）を 1 行ずつ出す。承認済みに数えるのは、確かめた confirm か approve の署名が指す版の読み方だけ。読み方の版は SHA-256 の全長で記録する。担当者の範囲の読み方には、署名する人の呼び名を渡す。自分の確定の署名で、Claude が書いた下書きも承認してよい。ただし一覧を見せてから（運営者の決定、2026-11-04）。
- **人だけの経路**：鍵を作る・署名する（確定・承認・差し戻し・戻す）・渡す・番を替える・鍵を確認済みにする。どれも許可の一覧に載せ、タブの秘密と 1 回きりの印と合言葉を求め、拒む試験を付ける（今の plan_commit を拒む試験は、署名の経路へ移す。消さない）。署名の鍵は橋渡しが合言葉で開き、署名したらすぐ捨てる。
- AI 向けの文（instructions・ツールの説明）は、署名ができるまで「人が確定した版」と言い、「署名で承認」と言わない。

#### 2.18.3 Skill を AI に渡す

決まり：Skill の文は AI への補いであって、安全の決まり（MCP の instructions の 1〜7）を上書きしない。どの Skill を渡すかは作業画面（人が選んだパックと施設）が決め、AI に選ばせない（§2.13）。

- **1 段（基本操作）**：MCP の instructions（Claude Code で効く）と同じ文から、`skills/moyai/SKILL.md` を作る（`src/shared/skill-moyai.ts`。試験で一致を確かめる）。Claude Desktop のために、利用者がアップロードする zip を作り、README に入れ方を書く。使い方の要点は、ツールの説明と結果の文にも書く（今のまま）。
- **2 段（業界のパック）**：`packs/<パック>/SKILL.md` を足す。日本語で、一次資料から書く（ごみ焼却を先に。し尿処理は短く）。中身は §2.17 の表のとおり。
- **3 段（独自の読み方）**：作業画面が当てている読み方（承認済み＋自分の下書き）の SKILL.md の本文と、規則の 1 文。SKILL.md は、規則から作る部分と、人が手で書いた部分（`## 補い` の下）に分け、作り直しても手で書いた部分を残す。
- **渡し方**：
  - どの結果（intake_survey・chart_rows・check_results・crosswalk_propose）にも、今効いている Skill の目録（段・名前・版）だけを添える。本文は添えない（結果の上限を食い、会話の数え方が Claude Desktop と Claude Code の /compact で当てにならないため）。
  - 本文は、intake_survey の part に `skills` を足して返す（段・名前・版・本文）。新しいツールは作らない（使わない名前の一覧に近い名前を作らないため）。
  - ツールの共通の説明に「目録の版が、前に読んだものと違えば、intake_survey（part: skills）で読み直す」と書く。
- 保存の前に、秘密らしい文字（API キーの形など）とほかの客先の名前を調べる（§2.13 のまま）。

#### 2.18.4 公開の台帳を計画に使う

決まり：台帳から読むのは、下限を守った帯と匿名の札だけ（§2.8）。計画に入れるのは、人が受けた案だけ。

- **読む**：peer_reference に、場を「公開の台帳」に固め、立場を「市町村」に固めた読み方を足す。見え方の軸の答えは、作業中の計画の施設から取り、無い軸は質問として返す。輪（非公開）の束は今どおり、人が比べを開いたときだけ。輪の数字が根拠の文（Excel と差分レポートに出る）に写らないことを試験する。人が比べを開かなくても、AI は公開の台帳の集計を読める（運営者の決定、2026-11-04。公開の台帳は誰でも読める公開物のため）。
- **反映**：chart_propose を作る。
  - 案は、作業のきっかけ（§2.4）の暦の枝として置く（`work.trigger` に周期の年数と月）。印を引く関数と、きっかけの次回の計算を 1 本にする。
  - 会期中は足すだけにする（今ある印を消さない）。実施と同じ年度は ◎ にする。起点は、号炉・系統ごとの最後の実施。最後の実施が無いとき、計画の終わりの年度が無いときは、置かずに質問を返す。
  - 根拠に、使った台帳の版（clone の commit）と集計（「似た施設 6 の帯 6〜8 年。前の実績 2024 年度から 5 年」）を書く。費用は書かない。
  - 台帳から来た計画の印には、出どころの型「台帳（版・集計）」を足す（明細は出どころが 1 つ以上要るため）。
  - 案は、決定のシートに案の ID ごとに 1 行で並ぶ（1 つの規則で数十の印を引いても 1 行）。星取表のシートでは朱の破線の円になる（`docs/screens.md` 3.2）。人が受けて署名するまで決まらない。
  - 根拠にする施設の数は n ≥ 5（中央の帯）だけ（送る側の k ≥ 5 とそろえる）。
  - 周期を直すのは会話でする（`docs/screens.md` 0）。画面に周期のダイアログは作らない（§2.2 の周期のダイアログは消す）。

### 2.19 施設の署名鍵（運営者の決定、2026-11-04）

束（輪・公開の台帳）に署名する鍵は、施設のもの。運営者の言葉：「キーは、施設ごとに持つ必要があります。どのPCからでも、その施設の最新が台帳に登録される必要があります。」「パスワードは絶対いやです。」（Architect のセッションを通して決めた。前の設計の「施設の合言葉」は使わない）

**決めたこと**

1. 計画のフォルダを開ける人なら、その施設として出せる。
   - 施設の署名鍵は、保管先の計画のフォルダ `plans/<計画ID>/share/keys/<場ID>.json` に、合言葉で包まずに置く。PC の登録も、人ごとに包むこともしない。
   - 委託先が替わるときは、計画のフォルダを渡すだけ。
   - 計画のフォルダを開ける人は、計画そのものも書き換えられる。台帳に出せる人を同じ範囲にしても、守りは弱くならない。公開の台帳には、もともと誰でも新しい鍵で出せる。
   - 出した束の記録（持ち出し簿）も、同じフォルダの `share/sent/` に置く。どの PC も、前の連番・ハッシュと、まだ載っていない PR を読める。
2. 鍵は施設 × 場（輪ごと・台帳ごと）に 1 つ（Architect が「A のまま」とし、運営者の反対は無かった。はっきりした答えはまだ）。輪の仲間に、公開の台帳のどの束があなたの施設かを、鍵から突き合わせられないようにするため。
3. 出した人の GitHub のアカウントが替わったら、台帳の検査が印を付ける。その鍵の前の PR と違うアカウントから PR が来たら「出した人が替わった」。台帳の管理者がマージする前に確かめる。
4. フォルダをなくしたら、前の鍵の続きにできる。
   - 計画を作り直すと、新しい署名鍵ができる。SHARE で「前の鍵の続きとして出す」を選び、前の鍵は、自分の GitHub のアカウントから前に出した PR の一覧から選ぶ。
   - PR に「新しい鍵は、前の鍵 ○○ の続き」と書く。検査は「古い鍵の署名なし」と印を付ける。
   - 管理者が確かめてマージしたら、古い鍵は引退し、新しい鍵が同じ施設の続きとして数えられる。確かめられなければ、別の施設として載る。古い鍵の分は、期限（例 2 年度）を過ぎたら数えない。
5. 鍵が漏れたら「署名鍵を作り直す」：新しい鍵を作り、古い鍵の引退の印（古い鍵自身の署名）を別のファイル（輪は `members/<鍵ID>.retired.json`）で足す。押せるのは計画のフォルダを開ける人（人だけの経路）。受け手は、引退の印を古い鍵自身の署名のときだけ受ける（ほかの仲間が他人の鍵を k から外せないように）。
6. 輪で連番がぶつかったとき（2 台がほぼ同時に出す、同期の遅れ）：
   - 防ぐ：送る前に保管先の持ち出し簿に「連番 N を使う」を書き、場と保管先を読み直す。ほかの PC の同じ連番が見えたら送らない。
   - 知らせる：同じ連番の束が 2 つあれば「鎖が分かれています」と出し、その場へ送るのを止める。
   - 直す：5 の「署名鍵を作り直す」（束は消さない。輪は足すだけのまま）。台帳では、ぶつかった PR は検証で ✗ になって載らないので、出し直せば次の連番で通る。

**守り（包まない鍵を置くので、足すこと）**

- AI に鍵の中身を出さない：
  - MCP のどのツールの結果にも、`share/keys/` の中身を入れない。保管先を読む処理（版の一覧・コメント・読み方・計画の版を読む）は、`share/keys/` を読まない。
  - シェルを持つ AI（Claude Code）は、ファイルを読む道具で保管先を読める。見張りのフック（`scripts/guard-hook.mjs`）に、保管先の `plans/*/share/keys/` の読み取りを止める決まりを足す（保管先の場所は、輪のフォルダと同じく、毎回状態の設定から読む）。.claude/settings.json の deny にも足す。
  - 「同じ利用者のプロセスは止めきれない」「計画のフォルダを読める人と AI は、鍵を写せる」を `docs/security.md` に書く。
- 保管先が OneDrive などの同期フォルダなら、鍵は会社のクラウドに上がる。SHARE に「施設の署名鍵は、計画のフォルダに置きます。フォルダを開ける人は、この施設として出せます。」を 1 行出す（戻せない操作の前の結果の文）。
- §2.12 の「秘密鍵は同期されない状態フォルダに置く」は、施設の署名鍵については、この節のとおりに変わる。人の鍵（版の署名）と GitHub のトークンは状態フォルダのまま。

**合わせて変わること**

- SHARE で束を送るとき、合言葉は打たない（輪も台帳も）。人だけの経路（タブの秘密と 1 回きりの印）で、人が押したときだけ送る。
- GitHub のトークンは、合言葉で包まずに状態フォルダ（同期されない。見張りのフックで AI の読み取りを止める）に置く。GitHub につなぐダイアログから合言葉の欄を外す。
- 前の設計の「施設の合言葉」「施設の鍵の scrypt（N=2^17）」は要らない。

**まだ決まっていないこと**

- 鍵の単位（2）の、運営者のはっきりした答え。
- （決まった）版の確定と承認の署名（人の鍵）も、合言葉をやめる（運営者「やめる」、2026-11-04）。人の鍵は、包まずに状態フォルダ（同期されない。見張りのフックで AI の読み取りを止める）に置く。署名は、人が画面で署名のボタンを押したとき（人だけの経路）に決まる。守りはその PC の Windows のアカウント。PC をなくしたら新しい鍵を足す（古い鍵は消さない）。Windows Hello で本人を確かめる形は、会期の後に足せる。

## 4. 作りの決まり

MOYAI を作るときの決まりです。

**つなぐ**

- 送る側と受ける側は同じ変更で作る。イベント・ツール・誤りの型は `src/shared/` の 1 か所に置き、どの型にも送り手と受け手があることを CI で数える。
- 「できた」は、入口から画面まで 1 本たどってから言う。部品は呼ぶ側と一緒に作る。誤りを受けて画面に出す処理を最初に作る。
- 欄の名前は型の 1 か所から取り、層をまたぐ試験を置く（取り込んだ実績で次回の予定が動く）。画面と裏は同じスキーマを使い、入口で型を確かめる。1 件の不正で全体を止めず、飛ばした件数を出す。

**決まらないものは聞く**

- 値が決まらなければ件数を添えて人に返す。既定値で埋めない。
- 同一性の鍵が同じときだけ同じものとする。名前が似ているだけではまとめない。
- どのセルにも行き先を付け、外したものには理由を付ける。鍵は一意に作り、ぶつからないことを試験する。
- 人の言葉での直しは決まった形で読み、「こう読みました」に人の「はい」をもらってから効かせる。言葉の一部だけを見て判定しない。否定の言い方を試験に入れる。
- いくつかの AI の出力をまとめるときは決まった規則でまとめ、まとめられないものは「不確か」として聞く。
- 広い表は列で切らず、列ごとの要約を渡す。

**AI とのやりとり**

- AI の出力はツールの型で受け、型から外れたら直さずに聞き直す。画面の流れは決まった状態の遷移で、AI の言葉で分岐しない。
- どの呼び出しにも時間の上限を付ける。成功は確かめてから出す。
- AI が使えない状態や、代わりの道で動いている状態は、必ず画面に出す。内部の言葉をプロンプトに出さない。
- AI だけで決めたものの一覧を画面に出し、人が受けるまで確定しない。

**作り方と試験**

- 直すのは一般の手がかりと一般の質問の形だけにする。ファイルごとの継ぎはぎをしない。直したら、新しい見ていないファイルで測り直す。
- 試験の資料を作る役と、それを読む役を分ける。
- 試験は一時のフォルダで行う。見つかった試験が 0 件なら失敗にする。
- モックを作らない。動かないものは「未実装」と書き、ダミーの値で埋めない。
- 測っていない数字は出さない。目標の値と測った値を分けて書く。
- 実機（この PC の Windows・Chrome / Edge、Claude Desktop）で早くから何度も通す。CI が緑でも、実機で通るまで「できた」と言わない。時間の上限は実機で測って決める。
- 作りは要る分だけ。推論は Claude に任せ、手元に推論エンジンを抱えない。ビルドした 1 つの版を動かす。依存の初期化が何を書くかを確かめる。

**画面**

- 星取表と検問所は運営者の画面の約束どおりに細部まで作り、断らずに変えない。
- 書き出しは人が見る様式にする。
- 色は CSS 変数の 1 か所。画面の言葉の一覧を先に作る。ボタンの言葉は裏の動きと合わせる。動かない部品は置かない。
- パックの確かめた度合いを画面に出し、照らしたものだけを `requirement` にする。
- サンプルは厚い正解の世界から書き分ける。
