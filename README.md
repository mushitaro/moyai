# MOYAI

**ごみ焼却施設の点検・修理の記録を 1 枚の星取表にそろえ、全国の似た施設と「何年ごとに・何人日で・何日かけて直しているか」を比べられるようにする道具です。**

- **作った人**：ごみ焼却プラントメーカーで 10 年、施設の保全（点検・修理の計画と記録）に関わってきた技術者です。
- **課題**：全国の市町村等のごみ処理事業経費は、令和 6 年度に約 2.45 兆円です。環境省の手引きは、発注する側の専門能力の不足を指摘し、ほかの自治体の契約事例を使うことや、知識を共有することを促しています（出典と数え方は [docs/impact.md](docs/impact.md)）。
- **MOYAI がすること**：
  1. 施設ごとに書式のばらばらな Excel・PDF・写真の記録を、手元の PC で読み、設備ごとの星取表にそろえます。1 施設だけでも、整備の歴史と周期が 1 枚で見え、確定した版を署名つきで積み重ねて後任に残せます。
  2. 施設名と金額を伏せたまま、整備の周期・工数・日数を、全国の似た施設と比べます（同じ区分の施設が 5 つ以上そろったときだけ）。保全の計画や見積もりの中身を考える材料を増やすのがねらいです。

星取表は、設備を行、年度を列にして、点検・修理をした年に ●、予定の年に ○ を付けた表です。行は国の手引きの機器リスト × 作業の種類（点検・分解整備・更新・基幹改良）でそろえます。ほかの設備へは、Skillパック（データ）を足して広げます。

- 動画：[MOYAI｜保全の記録を、紡ぎあう ― Built with Claude: Japan 2026](https://youtu.be/Qn6WKnjlH6s)（提出の版。下の「提出のあとに変えたこと」は入っていません）
- テーマ：本来、誰にでも届くべきものを。
- 資料・施設・拠点は、どれも【架空】です。

## 試し方

MOYAI のアカウントもログインも要りません。

| 要るもの | |
|---|---|
| PC | Windows か macOS（確かめたのは Windows 11。macOS は未確認） |
| Node.js | 22 以上（無ければ Claude が、聞いてから公式のもの〔nodejs.org か winget の OpenJS.NodeJS.LTS〕を入れる） |
| AI クライアント | Claude Desktop（Code のタブか Chat）か Claude Code |

1. チャットに、このリポジトリの URL（<https://github.com/mushitaro/moyai>）を渡し、「MOYAI をインストールして」と頼む。Claude が Node を確かめ、clone → `npm ci` → `npm run build` → `setup` をします。`setup` は、送信者の名前を聞き、何をどこに書くかをチャットで見せ、「はい」をもらってから書きます。Claude Desktop が開いていれば、閉じるのを待ってから設定に足すので、Desktop を 1 回開き直します。Claude Desktop には、clone の今の版を版ごとのフォルダ（`setup` が道を出す）に別に入れ、設定は版のフォルダの外の起動の台本（`launch.cjs`）を指します。clone はそのままです（MOYAI を直す人は `setup --dev` で clone を直に指します）。
2. 「デモして」と頼む。Claude が、ごみ焼却の Skillパックの【架空】の資料（`packs/waste-incineration/demo/`：施設台帳・星取表・作業日報）を画面に入れ、確認を 1 つずつ聞き、星取表を作ります。1 回の返事で進めるのは 1 段だけで、画面の変化を見ながら進みます。確定は人が HOSHITORI の確定のシートでします。
3. 「MOYAI を最新にして」と頼むと、Claude が `moyai_update` で mushitaro/moyai の main に新しい版があるかを読み、聞いてから別のフォルダで用意します（取得 → `npm ci` → build → 自己点検。失敗したら捨てて今の版のまま。前の版を 1 つ残す）。動いている MOYAI は止めず、切り替えは次の起動です。用意できると、作業画面の右下のビルドの版の字が朱になります。手元の変更がある・早送りで進めないときは断ります。
4. 「MOYAI をアンインストールして」と頼む。Claude が、保存先（計画の版・施設の署名鍵・資料）も消すかを聞き（既定は残す）、`uninstall` の中身を見せてから消し、最後にリポジトリのフォルダを、消す道を見せて聞いてから消します。

人がするのは、チャットで答えることと、画面での確定・署名・送信・承認だけです（例外の 2 つは「仕組み」の 5）。端末・ダウンロード・ドラッグは頼みません。署名鍵は最初の確定で作られ、パスワードはありません。手順の正本は `skills/moyai/SKILL.md`（「チャットで入れる・デモ・消す」）と `packs/waste-incineration/demo/README.md` です。

## 課題：似たプラントと、比べられない

僕は、ごみ焼却プラントメーカーで 10 年働きました（保全エンジニア 5 年、星取表の仕組みの開発とデータ移行 5 年）。十年前、ある市町村の保全の担当者に「全国と比べたい。御社ならできるよね？」と頼まれました。予算を説明するために、自分の施設の保全が妥当かを、全国の類似施設と比べて確かめたかったのです。僕は応えられませんでした。

ごみ焼却施設の保全は、次の 4 者で回っています。

| 立場 | 役目 |
|---|---|
| 持ち主（市町村） | 施設を持ち、税金で整備を頼む。焼却施設は 844（環境省『一般廃棄物処理実態調査結果（令和 6 年度）』施設の表で、「施設の改廃」の欄が空の施設の数。休止・廃止・新設の印のある施設を除く。報告書が公表する施設数とは数え方が違う。`packs/waste-incineration/sources.json`） |
| プラントメーカー | 施設を建てる |
| メーカー系列の保全の会社 | 建てたメーカーの系列として整備を請ける。基幹的設備の延命化工事は（特命）随意契約で結ぶ例が多い（環境省『廃棄物処理施設建設工事等の入札・契約の手引き』令和 7 年 3 月改訂、6 頁）。毎年の整備の契約の方法は、数えていません |
| O&M の事業者 | 運転と維持管理を、何年もまとめて請け負う |

応えられなかったのは、誰かが悪いからではなく、この形のためです。

- 全国の履歴を見ているのは、整備を請ける会社です。ほかの施設の履歴を見せれば、整備費を比べる材料になります。会社として、共有はできませんでした。
- せめて自社の記録で、その市町村の計画を整えようとしました。でも、データが整っていませんでした。1 施設の機器はおよそ 1,000〜2,000、整備は毎年、書類は客先の指定の書式です。作業日報・工事報告書・次の年の整備計画はつながっているのに、書式が違って分かれていました（僕の経験から）。データを整える費用が高すぎて、誰もシステムにしませんでした。
- 設備保全システムの会社に移っても、独立しても、行き着いた所は同じでした。データは、人が作るしかありませんでした。

いまは Claude がいます。どんな書式の資料でも読み、データを整えられます。ただ、日本の会社は、資料を AI に渡して学習されることを嫌います。だから MOYAI は、ほぼ手元で動きます。Claude に送るのは、表の形と、読みきれなかった一部だけです。全国で共有するのは、自治体と事業者が共有している書類の情報だけで、原価と施設名は出しません。

整備の履歴は施設ごと・請けた会社ごとに分かれ、書き方も施設ごとに違います。市町村は自施設の周期・工数・日数を、保全の会社は他社が建てたプラントを、O&M の事業者は入札の対象の類似施設を、それぞれ比べたいと考えています（僕の経験から）。

国の資料も、この形を書いています。環境省の手引き（令和 7 年 3 月改訂）は、技術とノウハウがプラントメーカーに集まり、発注する市町村には「プラントメーカーと対等に技術や価格等について交渉する専門的能力が不足している」とし（1 頁）、市町村どうしで知識を共有すること（5 頁）、予定価格はメーカーの見積書だけに頼らずほかの市町村の契約事例を集めて作ること（10 頁）を求めています。ごみの中間処理に関する建設工事・処理・委託・人件費の 4 費目は、令和 6 年度に合計約 1.3 兆円です（このリポジトリが選んで足した数で、補修整備だけの額ではありません。[docs/impact.md](docs/impact.md)）。

環境省が集めた自治体の計画では、焼却施設は稼働から 30 年ほどで、建設費と同じくらいの点検補修費を負担しています。その時期は施設によって大きく違い、全連続運転・発電付きの施設では 10 数年から 40 年ほどまで開きがあります（環境省『廃棄物処理施設長寿命化総合計画作成の手引き（ごみ焼却施設編）』119〜120 頁）。

公開されている費用の情報や計画はあります。MOYAI はそれに加えて、設備ごとの整備の周期・工数・日数を、条件をそろえて施設をまたいで比べるための物差しと場を作ります。

## 仕組み

### MOYAI がすること

1. **取り込み**：Excel・CSV・PDF・写真をそのまま入れる。Claude は資料の形（見出し・列・件数・小さな見本）を読み、未確定の所だけを聞く。行のデータは Claude に渡さない。
2. **星取表**：記録を共通台帳に紐付け、年度の列に並べる。共通台帳は、共通の設備項目（環境省『廃棄物処理施設長寿命化総合計画作成の手引き（ごみ焼却施設編）』表Ⅱ-4）× 作業分類（点検・分解整備・更新・基幹改良）。周期の案には根拠（自施設の実績・Skillパックの基準・公開台帳・計画ルール）を付ける。
3. **照査**：Skillパックの基準（出典つき）で、純粋な関数が基準外を出す。自己点検であって、審査の判断ではない。
4. **共有**：周期・工数・日数を階級（例：間隔 6〜7 年）に区切った値だけを、施設の署名鍵で署名して共有フォルダか公開台帳に送信する。同区分の施設が 5 に届かなければ送らない。費用・施設名・日付は出さない。
5. **確定は人だけ**：確定・署名・送信・承認は画面のボタンにだけあり、Claude のツールに無い（`docs/security.md`）。例外は 2 つ：人が「署名して渡す」を押したあと、利用者が頼めば Claude がその文のまま引き渡しのメールを送ること（リンクの中のワンタイムトークンは AI の提供者にも渡る）と、未承認のルールの下書きを保存先に書くこと。承認はどちらも人の署名。

### Skill の 3 段（`docs/plan.md` §2.17）

| 段 | 中身 | 置き場所 |
|---|---|---|
| 1 段目 | 標準の読み手と、操作の手順（入れる・取り込む・確定を頼む・詰めきれないときの手順） | `skills/moyai/SKILL.md`、`src/import/`、`packs/_cues/` |
| 2 段目 | 業種の Skillパック（共通の設備項目・照査・データの名前・業種の語のルール） | `packs/<業種>/`。ごみ焼却は `packs/waste-incineration/reading.json` にルールを置いた |
| 3 段目 | 会話で作るルール（施設・担当・会社ごと）。人が版に署名すると承認される | 利用者の保存先の `skills/` |

ルールを当てる順は 3 段目 → 2 段目 → 1 段目です。資料の形の読み（表・見出し・結合など）は 1 段目、業種の語は 2 段目、施設ごとの細かい読みは 3 段目に置きます。新しい施設は、Claude と利用者の会話を繰り返して 3 段目のルールで詰めます。1 段目と 2 段目に足すのは、どの施設の資料にも出る形だと示せたときだけです。

## 保証できないこと

### 共有（`docs/plan.md` §2.8、`docs/sharing.md`）

1. 共有フォルダのメンバーには、誰の共有ファイルか分かる。
2. 受け取った人は写せる。
3. 全国の表に無い知識との突合は防げない。
4. 紐付けの誤りは見つけられない。
5. 中身が本当かは示せない。
6. 共有先（OneDrive・GitHub など）は、置いた人の名前・時刻・ファイルの変更の記録を残す。
7. 共有ファイルの年度は相手に見える。
8. 共有先の管理者の隠し事は、署名でつないだ連番から後で気づけるだけ。
9. 差分プライバシーは無い。
10. AI の提供者へ渡る経路は別（下の節）。
11. 同じ PC の同じ利用者のプロセスは止めきれない。
12. 共有してよいか（契約・独禁法・営業秘密）は、アプリが決められない。
13. 公開台帳の共有ファイルは誰でも開け、PR の GitHub アカウント名は公開される。
14. 台帳のリポジトリの PR の検証（`ledger-validate`）を必須のチェックにしているかは未確認（11-12）。載せるかは、管理者（僕）が検証の結果と共有ファイルを見て、マージで決める。

### AI への提供範囲と PC の中（`docs/security.md`）

1. 1 回の上限は、繰り返し呼べば越えられる（会話の合計に上限を置く。合計はブリッジを止めると消える）。
2. チャットに Excel を添付すれば、ファイル全体が AI の提供者に渡る。
3. ファイルを読める AI は、確定した計画のファイルを直接読める。
4. Documents が同期フォルダ（OneDrive など）の下なら、確定した計画は会社のクラウドに上がる（起動のたびに調べて知らせる）。
5. 「外へは送らない」はアプリの通信の話で、データの行き先の保証ではない。例外として、入っている MOYAI は起動のときと 6 時間ごとに github.com の mushitaro/moyai の main に新しい版があるかを git で問い合わせる（送るのは問い合わせだけで、施設・行・鍵・設定の中身は送らない。設定の「最新の確かめ」を「しない」にすると一切問い合わせない）。
6. 写真の読取では、人が許したその画像が AI の提供者に渡る。
7. 画面を操作できる AI の道具（ブラウザやデスクトップの操作）は、人だけのボタンを押せる。
8. 計画のフォルダを読める人と AI は、施設の署名鍵を写せる（写した人は、その施設として送信できる）。保存先が同期フォルダなら、施設の署名鍵も会社のクラウドに上がる。
9. シェルを持つ AI は、見張りのフックを越えられる（スクリプトを書いて走らせる・`git apply`・`git reset` など）。フックが見るのは、道具の呼び出しの字だけ。
10. 施設の署名鍵のファイルを失くすと、その鍵の失効記録に署名できず、再発行した鍵と合わせて同じ施設を 2 つに数えることがある。
11. 費用の値を Claude の見本で伏せるのは、取り込みが費用の列と見分けた列だけ。ほかの言い方の見出し（「見込額」「予算額」「単価」など）の値は、見本に出ることがある。
12. `intake_add_files` のフォルダが、利用者がチャットで言ったものかを、ブリッジは確かめられない。AI が別のフォルダ（状態フォルダとリポジトリの外）を指せば、その直下の資料が画面に入り、要約の見本として AI に渡る（画面の作業の一覧に、AI が資料を入れたことが出る）。ネットワークの道（`\\server\share`・`//server/share`）は断る（`7987f48`）。
13. 公開台帳に載せた共有ファイルは、今は画面から取り下げられない。取り下げても、載ったファイルは消えず、受け取った人の複製も残る。

- 配布の形（`.mcpb`・自動更新）、ルールの施設をまたぐ使い回し。
- 手元のモデルで、データを外に出さずに紐付けをすること（F4）。

## 使わない仕組み

- **差分プライバシー・秘密計算**：送るのは決まった階級の値だけで、生の値は PC から出ない。値に雑音を足すと周期の根拠として読めなくなり、秘密計算は市町村の側にも同じ仕組みが要る。
- **P2P**：アプリは通信を持たない。共有フォルダの同期は OneDrive・Syncthing などに任せる。
- **合意の仕組み（ブロックチェーンなど）**：各施設は自分の場所に足すだけで、順は署名と前の共有ファイルのハッシュでつなぐ。公開台帳に載せるかは管理者（人）が PR のマージで決める。
